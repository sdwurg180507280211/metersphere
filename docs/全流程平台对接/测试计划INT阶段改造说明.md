# 测试计划 INT 阶段改造说明

## 1. 改造目标

测试计划页面面向普通使用者不再强调 MeterSphere 原有 6 个执行状态，而按 INT 业务流程展示更容易理解的业务阶段：

```text
需求已接收 → 测试计划 → 测试准备 → 测试执行 → 办结
```

其中真正的三个测试工作阶段为：

```text
测试计划 → 测试准备 → 测试执行
```

“需求已接收”是流程入口，“办结”是流程出口。

## 2. 与全流程平台的关系

正式流程不经过需求池人工建计划。

全流程平台通过 RocketMQ 同步需求后，测试平台应自动创建或更新对应测试计划。需求池仅保留为历史实现和 RocketMQ 双向交互技术参考，不作为当前业务流程入口。

目标交互如下：

```text
全流程平台
    │
    │ 需求创建/更新/取消、需求规格说明书、开发计划/实际完成时间、审批结果
    ▼
RocketMQ
    ▼
测试平台测试计划
    │
    │ 测试计划信息、测试阶段结果、实际时间、测试报告链接
    ▼
RocketMQ
    ▼
全流程平台
```

## 3. 阶段进入条件

| 阶段 | 进入条件 | 主要工作 | 退出条件/下一阶段 |
|------|----------|----------|-------------------|
| 需求已接收 | 全流程平台需求消息到达测试平台 | 接收需求编号、需求名称、所属系统等信息，并自动建立对应测试计划 | 测试计划创建完成，进入“测试计划” |
| 测试计划 | 测试计划已自动创建；需求规格说明书和开发计划完成时间等计划输入具备 | 编制测试计划，安排测试人员和时间，提交计划审批 | 全流程平台审批通过后进入“测试准备”；驳回则留在本阶段修改后重新提交 |
| 测试准备 | 全流程平台回传测试计划审批通过 | 需求分析、测试用例编制、用例评审 | 用例评审完成且满足测试执行准入条件后，等待开发实际完成；收到开发实际完成时间后进入“测试执行” |
| 测试执行 | 全流程平台同步开发实际完成时间，且测试准备已完成 | 冒烟测试、用例执行、缺陷提交与跟踪、缺陷复测 | 测试完成并生成、分享测试报告后进入“办结” |
| 办结 | 测试完成并完成报告分享 | 固化测试用例、缺陷、报告及实际执行结束时间 | 向全流程平台回传测试结果、实际执行结束时间和报告链接，本次 INT 流程结束 |

取消需求属于异常终止路径，不强行归入上述三个测试工作阶段。全流程平台同步取消后，对应测试计划应进入“已取消”。

## 4. 与原 6 个 TestPlanStatus 的关系

MeterSphere 原有状态：

```text
Prepare / Underway / Completed / Finished / Archived / Cancelled
```

继续作为系统内部执行状态保留，避免影响现有测试计划执行、报告、定时任务及其他模块。

对于全流程平台同步创建、带 `requirementNumber` 的测试计划：

- 页面主列表展示“当前阶段”，不再让普通使用者直接通过列表下拉修改 6 个底层状态；
- 业务阶段优先使用全流程对接产生的明确阶段字段；
- 不根据用例数量、通过率或时间字段猜测“测试准备”；
- 在后端业务阶段字段尚未落地前，只对能够从现有状态明确判断的阶段做兼容展示。

对于测试计划页面手工创建、没有 `requirementNumber` 的普通测试计划，继续保留原有 6 状态及现有操作方式。

## 5. 当前前端兼容规则

当前阶段组件优先读取明确的业务阶段字段：

```text
intStage / requirementFlowStage / workflowStage
```

兼容现有数据时：

| 当前数据 | 展示 |
|----------|------|
| status = Underway | 测试执行 |
| status = Completed / Finished | 办结 |
| status = Cancelled | 已取消 |
| status = Archived | 已归档 |
| requirementApprovalStatus = APPROVED | 测试准备 |
| 其他带 requirementNumber 的计划 | 测试计划 |

“测试准备”不能仅凭原 `Prepare` 状态判断，因为 `Prepare` 无法区分“测试计划编制中”和“计划审批通过后的测试准备”。正式对接时应由全流程平台审批结果或独立业务阶段字段明确驱动。

## 6. 后续后端对接要求

后续实现全流程平台正式驱动时，应补齐以下能力：

1. `CREATED` 消息直接创建测试计划，不写入需求池等待人工操作；
2. `UPDATED` 消息更新对应测试计划需求信息；
3. `CANCELLED` 消息取消对应测试计划；
4. 计划审批通过后明确写入“测试准备”阶段；
5. 收到开发实际完成时间后明确写入“测试执行”阶段；
6. 测试报告分享并完成交付后明确写入“办结”阶段；
7. 各关键节点通过 RocketMQ 向全流程平台回传计划信息、实际时间、状态和报告链接。

具体项目、模块节点和测试负责人的自动创建位置仍需依赖“所属系统 → 项目/模块/负责人”映射，映射关系未确认前不应在代码中猜测。

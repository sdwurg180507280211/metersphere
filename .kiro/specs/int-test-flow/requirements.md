# INT 测试平台整体需求规格

> 本文件覆盖本次 INT 测试平台改造的整体需求，从全研发流程平台需求进入测试平台开始，到测试计划办结结束。
> 本文件只描述需求、业务规则和可验证行为，不提前固化数据库、接口实现、消息中间件、算法等技术方案。
> 已明确的规则直接写入需求；仍存在业务或技术不确定性的内容统一放在“待确认/待技术评估”章节。
>
> **需求解释优先级：本 requirements.md 为当前 INT 测试平台业务需求基线。历史 `.kiro/specs`、旧需求文档及现有代码仅用于字段、兼容性和技术实现参考；当其内容与本文件冲突时，以本文件为准。现有代码结构不得反向约束或修改本文件中已经明确的业务需求。**

---

## 1. 总体目标

本次改造以“测试计划”为核心业务对象，把需求接入、人员排期、测试准备、用例、缺陷、测试执行、报告和办结串成一条完整 INT 测试主线。

主状态链统一为：

```text
待介入 → 测试计划 → 待审批 → 待测试准备 → 测试准备 → 待测试执行 → 测试执行 → 办结
```

总体原则：

1. 测试计划是 INT 测试过程的主业务对象。
2. 功能用例、缺陷、评审结果、实际时间、报告都围绕测试计划展开。
3. 状态不允许任意跳转，当前状态只允许进入合法的下一状态。
4. 自动流转只在明确条件满足时发生；需要记录真实开始/结束时间的节点由人员主动操作。
5. 全研发流程平台负责提供需求和开发相关信息；测试平台负责 INT 测试过程本身。
6. 全研发流程平台收到 INT 办结后进入什么后续流程，不属于本次测试平台需求范围。
7. 系统负责人审核、确认等动作属于全研发流程平台内部流程，不纳入测试平台状态和业务规则。
8. 测试计划不再提供人工新增入口，全部根据全研发流程平台传入的数据自动创建。
9. 测试计划页面只展示本文件定义的 INT 主状态，不再展示或使用 MeterSphere 原测试计划状态作为业务操作入口。
10. 原有历史测试计划保持原状，不批量转换为新版 INT 测试计划；新自动创建的 INT 测试计划进入本文件定义的新目录和新主流程。
11. 全研发流程平台会发送所有系统的数据，测试平台只接入本地所属系统映射表中已启用的指定系统数据。

## 2. 总需求编号、需求编号、所属系统与目录关系

测试平台目录结构为：

```text
所属系统
└─ 总需求编号-需求名称
   └─ 测试计划数据
```

### 2.1 总需求编号与需求编号的关系

1. “总需求编号”用于标识一条原始需求，是跨系统的上层业务标识。
2. 一条原始需求可以涉及多个系统，因此一个总需求编号可以关联多个需求编号。
3. “需求编号”用于标识原始需求落到具体系统后的系统需求，是测试计划需要保存的外部业务 ID；`dmpNum` 全局唯一，一个 `dmpNum` 永远只对应一个稳定测试计划。
4. 业务需求在全研发流程平台创建后，涉及的系统及各系统对应的需求编号已经确定；后续各系统负责人审核属于全研发流程平台内部流程，与测试平台无关。
5. 需求编号的前缀能够确定所属系统，不同系统使用固定的需求编号前缀。
6. “需求编号前缀 ↔ 所属系统”的对应关系为固定映射，由测试平台维护。
7. 全研发流程平台不会向测试平台传入“所属系统”字段，测试平台收到需求编号后，应根据需求编号前缀和本地维护的映射关系确定所属系统。
8. 同一总需求编号下，不同需求编号可以分别归属不同系统，并分别形成对应系统目录下的测试计划数据。

本次已确认的业务字段与上游字段映射如下：

| 业务字段 | 上游字段 | 含义 |
|---|---|---|
| 总需求编号 | `parentWfinstCode` | 标识一条跨系统的原始需求，并用于生成“总需求编号-需求名称”目录 |
| 需求编号 | `dmpNum` | 标识原始需求落到具体系统后的系统需求，是全局唯一的外部业务 ID，并作为测试计划业务字段 |
| 需求名称 | `name1` | 原始需求名称，并参与生成“总需求编号-需求名称”目录和测试计划展示信息 |

以上三个字段名称属于当前已确认对接字段，后续设计和实现不得再把 `dmpNum` 解释为总需求编号。

`dmpNum` 只作为全研发流程平台侧的外部业务 ID 和测试平台识别同一计划的稳定业务标识，不要求其物理值等于 MeterSphere 内部的 `test_plan.id`；`test_plan.id` 继续作为 MeterSphere 内部稳定主键。

业务关系可理解为：

```text
总需求编号（parentWfinstCode）
├─ 需求编号 A（dmpNum）→ 前缀映射 → 所属系统 A → 测试计划数据
├─ 需求编号 B（dmpNum）→ 前缀映射 → 所属系统 B → 测试计划数据
└─ 需求编号 C（dmpNum）→ 前缀映射 → 所属系统 C → 测试计划数据

需求名称 = name1
```

### 2.2 系统映射维护

测试平台需要维护用于 INT 流程识别和人员匹配的系统基础映射，业务关系至少包括：

```text
需求编号前缀
    ↓
所属系统
    ↓
测试组/用户组
    ↓
测试团队负责人
```

要求：

1. 需求编号前缀与所属系统的映射由测试平台维护，不依赖全研发流程平台传入所属系统。
2. 映射表至少维护需求编号前缀、所属系统、测试组/用户组、测试团队负责人和是否启用。
3. 每个已启用的需求编号前缀应唯一对应一个所属系统，并且必须配置测试组和测试团队负责人。
4. 当前缀存在包含关系时，必须采用最长前缀匹配，例如优先匹配 `DR-INER-MT` 而不是 `DR-INER`、优先匹配 `CMS2.0` 而不是 `CMS`。
5. 只有匹配到已启用映射的数据才进入 INT 主流程；未匹配或映射未启用的数据不创建目录、不创建测试计划，也不猜测或创建“未知系统”。
6. 被过滤的数据应保留需求编号、原始消息、过滤原因和时间等可追溯信息；后续补齐并启用映射后，允许对历史过滤记录人工重试。
7. 所属系统、测试组和测试团队负责人分别用于目录归属、通知范围和测试计划负责人赋值，不得用“测试组第一个成员”替代已配置的负责人。
8. 映射关系的具体维护页面、数据库结构及与 MeterSphere 现有项目/模块配置的兼容方式属于技术设计内容，不在本文件固定。

### 2.3 目录规则

1. “所属系统”由测试平台根据需求编号前缀映射得到，并据此创建或定位对应目录。
2. “总需求编号-需求名称”根据全研发流程平台传入的原始需求信息自动创建或定位，其中总需求编号取 `parentWfinstCode`，需求名称取 `name1`。
3. 上述两级属于系统自动创建的业务目录层级。
4. 上述系统自动创建的业务目录不提供人工修改、移动、重命名或删除入口。
5. 如果通过其他非标准方式修改了自动业务目录，相关后果由操作方承担；本次不要求平台提供兼容、自动修复、自动还原或数据纠错能力。
6. 目录名称保存创建时的 `name1` 快照；同一 `dmpNum` 后续收到新的 `name1` 时，可以更新需求名称和测试计划名称，但已创建目录不自动重命名。
7. “需求编号”是测试计划数据的业务字段，不作为目录层级；全研发来源字段为 `dmpNum`。
8. 同一“所属系统 + 总需求编号”下面允许存在多条测试计划数据，不按一对一关系限制。
9. 需求编号前缀映射出的所属系统还可继续用于匹配测试组、测试团队负责人和通知对象。

### 2.4 原始需求类型

原始需求目前包括：

- 原始业务需求
- 系统优化需求

原始业务需求可携带业务需求 ZIP 包链接。

## 3. 需求接入与测试计划数据创建

### 3.1 需求进入测试平台

测试计划只允许由全研发流程平台传入的数据自动创建。测试计划列表和目录页面不再提供人工新增测试计划入口。

全研发流程平台会发送所有系统的数据。测试平台以已启用的所属系统映射作为接入白名单，只对匹配到指定系统的数据执行后续自动创建流程。

全研发流程平台向测试平台传入可进入 INT 的需求数据时，当前至少需要包含：

- 总需求编号：`parentWfinstCode`
- 需求名称：`name1`
- 需求类型
- 需求编号：`dmpNum`
- 原始业务需求的业务需求 ZIP 包链接（如有）

全研发流程平台不传“所属系统”。测试平台收到数据后：

1. 读取 `dmpNum`，按最长前缀规则匹配已启用的所属系统映射。
2. 未匹配到已启用映射时，记录为已过滤并结束处理，不创建任何 INT 业务数据。
3. 匹配成功后，创建或定位该“所属系统”目录。
4. 根据 `parentWfinstCode` 和 `name1` 在所属系统下创建或定位“总需求编号-需求名称”目录。
5. 在该目录下自动创建对应的测试计划数据。
6. 测试计划数据初始状态为“待介入”。
7. `dmpNum` 作为需求编号保存为测试计划业务字段。
8. 测试计划名称自动取 `name1`，负责人自动取所属系统映射中的测试团队负责人。
9. 此时等待需求规格说明书和开发计划预期完成时间等外部字段继续补齐。

系统负责人是否已审核、审核顺序以及全研发流程平台内部如何控制发送时点，不作为测试平台判断条件。测试平台只处理全研发流程平台实际发送并可进入 INT 的需求数据。

### 3.2 同一总需求下多个需求编号分批进入

同一 `parentWfinstCode` 下可以存在多个 `dmpNum`，不同需求编号可以分批进入测试平台。

当测试平台后续收到同一总需求编号下新的需求编号时：

1. 根据新 `dmpNum` 的前缀映射出对应所属系统。
2. 创建或定位该系统对应的“所属系统”目录。
3. 在该系统下创建或定位相同“总需求编号-需求名称”目录。
4. 按新的 `dmpNum` 创建对应测试计划数据。
5. 不影响同一总需求编号下已经存在的其他系统或其他需求编号对应的测试计划数据。

### 3.3 重复同步与后续字段更新

为避免外部平台重试、重复发送造成重复业务数据，需要满足以下业务结果：

1. 同一需求编号 `dmpNum` 重复同步时，不得重复创建新的测试计划数据。
2. 测试平台应识别已经存在的需求编号，并将后续允许更新的外部字段更新到原测试计划数据或其 INT 扩展数据中。
3. 需求规格说明书、开发计划预期完成时间、开发实际完成时间等后续消息属于同一需求编号的字段补充或更新，不重新创建测试计划。
4. 同一总需求编号 `parentWfinstCode` 下出现新的 `dmpNum` 时，才按新的系统需求创建新的测试计划数据。
5. `dmpNum` 在测试计划业务数据中必须满足全局唯一约束，并作为外部消息定位稳定测试计划的业务键；具体索引、消息 ID 和重试机制由 design.md 定义。
6. 同一 `dmpNum` 后续收到新的 `name1` 时，更新测试计划保存的需求名称和只读计划名称，但不自动重命名已经创建的目录。
7. 同一 `dmpNum` 后续出现不同 `parentWfinstCode` 或匹配到不同所属系统时，应作为数据冲突记录并停止自动更新，不得移动原计划或创建第二个计划。
8. 本期只处理本文件已明确的需求接入和字段补充消息；独立的需求撤回、需求取消等非主流程事件暂不改变新版 INT 测试计划状态。

### 3.4 待介入数据补充

进入“待介入”后，以下信息可以分开到达：

- 需求规格说明书链接
- 开发计划预期完成时间

当两项同时存在时，测试计划自动从：

```text
待介入 → 测试计划
```

不得因为只收到其中一项而提前进入“测试计划”。

进入“测试计划”时，同时通知匹配到的测试组成员。

### 3.5 与现有需求池的关系

现有需求池的业务逻辑和一对一关联方式不再适用于本次 INT 测试主流程，本次需求不沿用现有需求池的接入、流转和测试计划创建逻辑。

要求：

1. INT 测试计划直接根据全研发流程平台传入的数据和本文件定义的规则自动创建，不以现有需求池记录作为创建前提。
2. 不使用现有需求池的单个关联计划关系限制 INT 测试计划数量。
3. 现有需求池中的字段名称、字段类型和已有数据含义可以作为新字段设计和数据映射的参考。
4. 对现有需求池逻辑的兼容、迁移或改造不作为本次 INT 主流程的前置条件。
5. 现有需求池中与更新、撤回、取消有关的代码可以保留，但不得直接消费新版 INT 主流程消息或修改新版 INT 测试计划状态。

### 3.6 历史测试计划与新版 INT 计划

1. 原有历史测试计划保留现有数据，不删除、不批量迁移、不强制补齐 INT 扩展数据，也不自动进入本文件定义的 INT 状态机。
2. 新接入的指定系统数据自动创建新版 INT 测试计划，并进入“所属系统 → 总需求编号-需求名称”的新目录结构。
3. 是否属于新版 INT 计划必须由明确的业务标识判断，不得通过计划名称、目录名称或创建时间猜测。
4. 新版 INT 页面只处理新版 INT 测试计划；历史普通测试计划继续保留原有访问和处理方式。

## 4. 测试计划状态机

### 4.1 状态链

测试计划列表、详情和编制页面只展示以下 INT 主状态。MeterSphere 原测试计划状态不再展示，也不作为 INT 测试计划筛选、流转或操作的依据。

```text
待介入
→ 测试计划
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

### 4.2 状态流转要求

1. 当前状态只展示合法下一状态或合法操作。
2. 自动流转节点不允许人员手工跳转。
3. “待介入 → 测试计划”为条件满足后的自动流转。
4. “测试计划 → 待审批”为提交测试计划后的人工操作。
5. “待审批 → 待测试准备/测试计划”为审批结果触发。
6. “待测试准备 → 测试准备”必须由人员点击“开始测试准备”。
7. “测试准备 → 待测试执行”必须由人员点击“完成测试准备”。
8. “待测试执行 → 测试执行”必须由人员点击“开始测试执行”。
9. “测试执行 → 办结”必须满足办结校验后由人员操作。
10. 人工开始/完成动作需要记录对应实际时间。
11. 冒烟测试不作为独立主状态。
12. 不提供通过原测试计划状态下拉框或通用编辑动作修改 INT 主状态的入口。

### 4.3 状态与操作角色

当前状态操作责任按以下业务角色理解：

| 当前状态/动作 | 主要操作角色 | 说明 |
|---|---|---|
| 待介入 | 系统自动 | 等待外部字段补齐，不允许人工强制跳转 |
| 测试计划编制、提交 | 测试团队负责人 | 编制准备/执行排期并提交审批 |
| 待审批：通过/驳回 | 测试总负责人 | 审批发生在测试平台 |
| 开始测试准备 | 测试人员 | 记录实际准备开始时间 |
| 完成测试准备 | 测试团队负责人/授权人员 | 填写线下评审信息并结构化导入评审后用例 |
| 开始测试执行 | 测试人员 | 先校验开发实际完成时间 |
| 测试执行、缺陷处理、办结 | 具备对应权限的测试人员 | 办结必须满足后端校验 |

具体 MeterSphere 权限点和角色绑定方式由 design.md 设计；业务角色权限不得突破本状态机允许的流转范围。

多人场景统一按以下规则处理：

1. 当前阶段任一已分配测试人员或测试团队负责人可以执行“开始测试准备”“开始测试执行”。
2. “完成测试准备”和“办结”由测试团队负责人或具备对应 INT 操作权限的人员执行。
3. 计划级开始/完成动作只流转一次，不要求每名参与人员分别确认。
4. 每次计划级操作必须记录实际操作人和操作时间；准备/执行参与人员仍以当前有效计划版本中的全部人员为准。

## 5. 测试计划编制

### 5.1 准备与执行分别排期

测试准备人员与测试执行人员允许不同，分别维护计划安排。

测试准备安排至少包括：

- 执行人
- 计划准备开始日期
- 计划准备结束日期

测试执行安排至少包括：

- 执行人
- 计划执行开始日期
- 计划执行结束日期

要求：

1. 同一阶段支持多人，可通过多行分别维护。
2. 每个人单独维护自己的开始日期和结束日期。
3. 准备人员和执行人员可以完全不同。
4. 同一人员也可以同时参与准备和执行。
5. 当前计划编制页面中的可填写项均按必填处理。
6. 是否需要冒烟测试使用单选方式选择。

### 5.2 测试计划页面字段控制

测试计划编制时：

1. 负责人根据 `dmpNum` 所属系统映射中的测试团队负责人自动赋值，页面置灰，不允许在当前计划编制动作中修改。
2. 计划名称自动取需求名称 `name1`，页面置灰，不允许在当前计划编制动作中修改。
3. 需求编号作为测试计划业务字段展示/保存。
4. 隐藏 MeterSphere 原“测试阶段”下拉框，不作为本次 INT 主流程的操作入口。
5. 测试计划名称不是唯一标识，不用于识别重复计划；不同所属系统目录下允许存在同名测试计划，稳定识别只使用全局唯一的 `dmpNum`。
6. 自动创建测试计划时使用专门的系统服务账号作为创建人，具体 MeterSphere 用户 ID 通过配置确定。
7. 隐藏 MeterSphere 原测试计划状态展示和状态修改入口，只展示当前 INT 主状态及其合法操作。

### 5.3 整体计划时间

当计划中存在多名准备人员和执行人员时：

- 整体测试准备开始时间取所有准备安排中的最早开始时间。
- 整体测试执行结束时间取所有执行安排中的最晚结束时间。
- 对外同步整体计划周期时，使用“最早测试准备开始时间 + 最晚测试执行结束时间”。

### 5.4 提交测试计划

测试团队负责人完成计划编制后提交，状态从：

```text
测试计划 → 待审批
```

提交后等待测试总负责人审批。

## 6. 测试计划审批

测试计划审批在测试平台完成，不在全研发流程平台完成。

测试总负责人审批后：

- 审批通过：`待审批 → 待测试准备`
- 审批驳回：`待审批 → 测试计划`

审批要求：

1. 审批通过和审批驳回均可以填写审批意见。
2. 审批意见当前均不强制必填。
3. 审批驳回后，测试团队负责人可以根据意见修改计划后再次提交。
4. 审批通过后，测试平台向全研发流程平台同步最新有效测试计划信息。
5. V1 以及后续每个调整版本 V2、V3 等都必须独立提交并由测试总负责人审批，调整版本不得绕过审批直接生效。
6. 每个计划版本的每轮提交、审批通过和审批驳回都必须完整留痕，不得使用最新结果覆盖历史记录。
7. 审批历史至少保留计划、计划版本、审批轮次、动作、提交人或审批人、操作时间和审批意见。
8. 驳回后修改并重新提交仍属于同一计划版本的下一审批轮次；只有发起下一次独立调整时才创建下一个版本。

## 7. 人员排期、空闲时间与冲突统计

人员排期能力需要同时解决两个问题：

1. 编制计划前能看出谁有空。
2. 保存计划时能发现人员是否与其他计划冲突。

### 7.1 冲突判断规则

编制或调整测试计划时，系统应检查执行人在目标日期范围内是否已被其他测试计划占用。

规则如下：

1. 查询该人员在其他“未办结”测试计划中的最新有效排期。
2. 测试准备排期和测试执行排期统一参与人员占用判断。
3. 按自然日期区间是否重叠判断冲突。
4. 不考虑法定节假日、调休、补班。
5. 暂不处理半天级冲突。
6. 暂不处理小时级冲突。
7. 暂不计算复杂负载百分比。
8. 存在冲突时明确提示，但允许继续保存测试计划。
9. 冲突提示应能看到相关测试计划、阶段和冲突日期范围。

### 7.2 人员排期统计

测试平台需要提供独立的人员排期统计能力，用于负责人在编制计划前按人员空闲情况划分任务。

用户可以指定统计日期范围，系统至少应统计和展示：

- 人员
- 已占用日期/天数
- 空闲日期/天数
- 冲突日期/天数
- 已排测试计划数量
- 具体测试计划
- 所属系统
- 需求编号
- 阶段（测试准备/测试执行）
- 计划开始日期
- 计划结束日期

占用区间存在重叠时，需要先合并日期区间再计算已占用天数，不能简单把不同计划天数直接相加。

空闲日期应基于用户选择的统计日期范围减去已占用日期得到。

冲突日期是同一人员在同一天存在两个或以上计划排期的日期。

### 7.3 Excel 导出

人员排期统计需要支持导出 Excel。

导出内容至少包括：

- 人员
- 统计开始日期
- 统计结束日期
- 已占用天数
- 空闲天数
- 冲突天数
- 已排计划数
- 测试计划
- 需求编号
- 所属系统
- 阶段
- 计划开始日期
- 计划结束日期
- 是否冲突

## 8. 测试计划调整

需求变化后，不直接覆盖原测试计划排期，也不创建新的测试计划主对象，而是在同一个稳定 `test_plan.id` 下新增**计划版本**。

```text
计划版本 V1（EFFECTIVE，继续生效）
→ 新增计划版本 V2（DRAFT）
→ 修改人员/时间并填写调整原因
→ 提交 V2 审批
→ V2 待审批
   ├─ 通过：V1 失效，V2 成为最新有效版本
   └─ 驳回：V1 继续生效，V2 返回可修改
```

测试计划主状态和计划版本审批状态相互独立。例如测试计划已经进入“测试准备”或“测试执行”时，提交 V2 不得把测试计划主状态回退到“待审批”。

计划版本只版本化以下信息：

- 测试准备人员及各自计划准备开始、结束日期。
- 测试执行人员及各自计划执行开始、结束日期。
- 调整原因。
- 该版本的提交、审批轮次和审批结果。

`test_plan.id`、`dmpNum`、`parentWfinstCode`、所属系统、需求名称以及计划关联的用例、缺陷和报告归属不随 V1/V2 调整而创建新主对象。

要求：

1. 原计划版本保留，不覆盖，不删除。
2. 每次独立调整形成一个新版本；驳回后修改、重新提交仍使用当前版本，不重复新增版本。
3. V2/V3 等调整版本审批通过前，当前有效版本继续生效。
4. 调整版本审批通过时，原有效版本变为历史版本，新版本成为唯一最新有效版本。
5. 调整版本审批驳回时，原有效版本不变，驳回版本返回可编辑状态并允许再次提交。
6. 只有审批通过后的最新计划时间、人员和调整原因才同步给全研发流程平台。
7. 创建或保存调整草稿本身不立即通知测试人员；提交审批时通知测试总负责人。
8. 后续测试准备提醒、测试执行提醒、人员空闲统计和冲突判断均以最新有效版本为准。
9. 审批中的草稿版本不参与正式提醒、人员占用和对外同步，但保存或提交时仍需要进行冲突提示。
10. 本节的“计划版本 V1/V2”仅指测试计划排期和审批版本，与第 10 节“评审后用例基线/最终用例版本”是两个不同概念。

## 9. 待测试准备与测试准备

### 9.1 准备提醒

到达最新有效计划的准备开始日期当天 09:00，提醒对应测试准备人员可以开始测试准备。

### 9.2 开始测试准备

测试人员在“待测试准备”状态点击“开始测试准备”后：

1. 状态进入“测试准备”。
2. 记录实际准备开始时间。

不得仅因为到达计划准备开始日期而自动进入“测试准备”。

### 9.3 完成测试准备

INT 用例在线下编写并完成线下评审，不使用 MeterSphere 原“用例评审”模块作为本次 INT 主流程入口。线下评审完成后，测试人员在测试平台通过评审弹窗登记结果并导入评审后用例。

测试人员点击“完成测试准备”时，系统打开线上评审弹窗，至少包含：

- 评审结果：必填，默认选择“通过”，允许改为“不通过”。
- 评审人员：必填，支持记录实际参加线下评审的人员。
- 评审意见：评审通过时可选，评审不通过时必填。
- 评审后用例 Excel：评审通过时必须上传；评审不通过时允许不上传。

评审结果为“通过”时：

1. 系统解析评审后 Excel，校验文件模板、必填字段和每一行数据。
2. 解析成功后，将用例结构化导入当前测试计划用例，不能只把 Excel 保存为附件或临时解析记录。
3. 首次评审通过且导入成功的数据保存为该测试计划的“首次评审后用例基线”。
4. 全部导入成功后记录实际准备结束时间，状态从“测试准备”进入“待测试执行”。
5. 任意文件级或行级错误都视为导入失败，保持“测试准备”，不记录实际准备结束时间，并向用户展示可定位的错误原因。

评审结果为“不通过”时：

1. 保存本轮评审结果、评审人员、评审意见、操作人和时间。
2. 测试计划继续保持“测试准备”，不得进入“待测试执行”。
3. 测试人员整改后重新发起线上评审；重新评审形成新的评审轮次，不覆盖此前记录。

所有评审轮次和上传记录都必须完整保留；只有“评审通过 + 评审后用例结构化导入成功”才能完成测试准备。

## 10. 用例上传、最终用例与版本识别

### 10.1 当前实际使用方式

测试人员主要在本地 Excel 中维护用例，不要求在测试平台页面逐条编辑。

当前流程：

```text
完成测试准备时上传并结构化导入评审后用例
→ 保存首次评审后用例基线
→ 测试执行期间继续在本地 Excel 中维护
→ 办结前上传最终实际用例
→ 与首次评审后用例基线比较
→ 生成新增/删除/修改汇总
→ 将最终用例全量同步为当前测试计划用例
```

测试执行期间允许在本地：

- 新增用例
- 修改用例
- 删除用例
- 调整用例顺序
- 更新最终执行状态

### 10.2 最终用例状态

办结前最终实际用例只允许存在：

- 通过
- 跳过

不得存在：

- 未执行
- 不通过
- 阻塞

### 10.3 用例稳定标识原则

为支持最终 Excel 与首次评审后用例基线的可靠差异识别，每条计划用例必须具有稳定且不随排序变化的“计划用例 ID”。

1. Excel 行号不能作为用例身份。
2. 页面排序序号不能作为用例身份。
3. Excel 调整排序后不能影响同一条用例的识别。
4. 首次评审后用例导入时，如果源 Excel 没有计划用例 ID，由平台为每条用例生成稳定 ID。
5. 平台生成的稳定 ID 必须能够回写或导出到测试人员后续维护的 Excel 中，并在最终上传时保持不变。
6. 最终 Excel 中已有稳定 ID 的行用于识别原用例；没有稳定 ID 的行按新增用例处理并生成新 ID。
7. 最终 Excel 出现重复稳定 ID、属于其他计划的 ID 或无法识别的 ID 时，导入失败，不得猜测匹配。
8. 页面展示序号与稳定计划用例 ID 必须是两个概念。

### 10.4 用例版本与差异比对

测试平台必须保留至少两类结构化用例版本：

- **首次评审后用例基线**：第一次“评审通过且结构化导入成功”的用例数据，作为后续差异比较的固定基线，不被最终 Excel 覆盖。
- **最终实际用例版本**：办结前最近一次校验并导入成功的最终 Excel 数据。

最终 Excel 上传后，系统必须基于稳定计划用例 ID 与首次评审后用例基线进行比较，并给出至少以下汇总：

| 差异类型 | 识别规则 |
|---|---|
| 新增 | 最终 Excel 中存在、首次评审后用例基线中不存在的稳定 ID，或者最终 Excel 中无稳定 ID 的新行 |
| 删除 | 首次评审后用例基线中存在、最终 Excel 中不存在的稳定 ID |
| 修改 | 两个版本中稳定 ID 相同，但除行号和页面排序外的纳入比较字段存在变化 |

差异结果至少展示新增数量、删除数量和修改数量，并保存本次比较结果。具体纳入比较的 Excel 字段和字段级差异展示由 design.md 明确，但不得把单纯调整 Excel 行顺序计为修改。

最终 Excel 校验成功后，采用全量同步方式形成当前测试计划用例：

1. 新增用例写入当前计划并生成稳定 ID。
2. 修改用例按稳定 ID 更新。
3. 删除用例按稳定 ID 从当前有效计划用例中删除或标记失效，并保留版本历史。
4. 未发生变化的用例保持原稳定 ID。
5. 每次最终 Excel 上传和差异结果都保留历史；重新上传最终 Excel 时仍然与固定的首次评审后用例基线比较。
6. 最终 Excel 解析、差异比较或全量同步任一步失败时，不得使用不完整数据办结。

### 10.5 最终用例办结数据源

办结时的用例状态校验、统计和报告必须读取最终 Excel 成功结构化导入并全量同步后的当前测试计划用例，不得直接读取未解析附件，也不得仅依赖上传批次中的临时数据。

## 11. 待测试执行与测试执行

### 11.1 执行提醒

到达最新有效计划的执行开始日期当天 09:00，提醒相关测试执行人员。

开发实际完成时间晚于计划执行开始日期时，不改变原计划提醒规则。

### 11.2 开始测试执行

测试人员在“待测试执行”状态点击“开始测试执行”时，系统必须校验全研发流程平台是否已经提供“开发实际完成时间”。

如果未提供：

- 弹窗提示“开发实际完成时间未提供，不能流转”。
- 状态继续保持“待测试执行”。

如果已经提供：

- 状态进入“测试执行”。
- 记录实际执行开始时间。

“开发实际完成时间”到达本身不得自动把状态推进到“测试执行”。

## 12. 冒烟测试

是否需要冒烟测试在测试计划编制阶段确定。

如果计划标记“需要冒烟测试”，正式执行用例前先进行冒烟测试。

冒烟测试属于测试执行阶段的前置过程，不单独增加主状态。

冒烟测试至少记录：

- 结论：通过/不通过。
- 实际执行人。
- 执行时间。
- 备注。
- 关联缺陷（如有）。

规则如下：

1. 不需要冒烟测试的计划进入“测试执行”后可以直接执行正式用例。
2. 需要冒烟测试的计划进入“测试执行”后，在冒烟测试通过前禁止执行正式用例。
3. 冒烟测试不通过时，测试计划继续保持“测试执行”，记录本轮结果并允许新增或关联缺陷。
4. 问题处理后可以重新进行冒烟测试，每次结果完整保留，不覆盖历史。
5. 最近一次冒烟测试结论为“通过”后，才允许继续正式用例执行。
6. 冒烟测试记录和关联缺陷应进入最终测试报告。

## 13. 测试计划与缺陷

### 13.1 缺陷关系

缺陷以测试计划为主关联对象，具体测试计划用例为可选关联对象。

```text
测试计划
└─ 缺陷（必须属于测试计划）
   └─ 具体测试计划用例（可选）
```

要求：

1. 测试计划页面增加“关联缺陷”视图。
2. “关联缺陷”展示当前测试计划下的全部缺陷。
3. 全局“缺陷管理”页面继续保留。
4. 测试计划缺陷不是新建一套缺陷数据，只是在当前测试计划上下文中查看和操作全局缺陷数据。

### 13.2 从测试计划新增缺陷

在测试计划“关联缺陷”页面点击新增缺陷时：

1. 缺陷必须关联当前测试计划。
2. 不强制关联具体用例。
3. 用户可以选择某条测试计划用例作为次级关联。

因此环境、部署、数据、公共问题、冒烟问题等没有明确用例归属的缺陷，也可以正常归属于测试计划。

### 13.3 从具体用例新增缺陷

从某条测试计划用例中新增缺陷时：

1. 自动关联当前测试计划。
2. 自动关联当前测试计划用例。

### 13.4 解除用例关联

如果一个缺陷已经属于测试计划，并同时关联某条测试计划用例，则解除“缺陷-用例”关系时：

- 只解除具体用例关系。
- 缺陷仍然保留在当前测试计划中。

### 13.5 技术兼容确认

以下两项需要结合现有后端实现继续确认：

- 新增缺陷接口是否支持只关联测试计划、不传计划用例。
- 解除用例关联时是否能够保留测试计划关联。

## 14. 测试计划办结

办结动作发生在测试平台。

办结前必须由后端进行完整校验，不能只依赖前端按钮状态。

### 14.1 用例校验

办结前必须已经成功上传并结构化导入最终 Excel，完成与首次评审后用例基线的差异比较，保存新增/删除/修改数量，并将最终版本全量同步为当前测试计划用例。

最终实际用例只能为：

- 通过
- 跳过

存在以下任一状态时禁止办结：

- 未执行
- 不通过
- 阻塞

### 14.2 缺陷校验

办结校验以缺陷管理页面“状态”自定义字段为准，不以 `issues.status` 等旧状态列或展示缓存为准。

当前本地状态自定义字段中，以下两个选项满足办结状态条件：

| 自定义字段选项值 | 展示名称 | 办结判定 |
|---|---|---|
| `closed` | 已关闭 | 允许办结 |
| `cancelled` | 已取消 | 允许办结 |

`new`、`accepted`、`resolved`、`reopened`、`invalid`、`on_hold` 等其他状态均不满足办结条件。因此，当前测试计划关联的每条缺陷必须处于以下任一状态：

```text
已关闭
或
已取消
```

只认“已关闭”或“已取消”。

存在任意既非“已关闭”也非“已取消”的缺陷时禁止办结。

办结校验必须按测试计划维度查询全部缺陷，不能只汇总具体用例下的缺陷，否则会漏掉没有关联具体用例的计划级缺陷。

### 14.3 办结成功

校验通过后：

1. 完成报告生成/保存/分享。
2. 记录实际执行结束时间。
3. 测试计划状态进入“办结”。
4. 向全研发流程平台同步办结状态、实际执行结束时间和报告链接。

## 15. 消息通知

测试平台需要根据所属系统找到对应测试组，并向相关人员发送处理提醒。所属系统由需求编号前缀与测试平台维护的固定映射关系确定。

当前测试组按“用户组”理解。

通知至少用于：

- “待介入 → 测试计划”后通知匹配到的测试组成员。
- V1 或调整版本提交审批后通知测试总负责人。
- 最新有效计划准备开始日期当天 09:00 提醒准备人员。
- 最新有效计划执行开始日期当天 09:00 提醒执行人员。

优先考虑复用项目现有右上角抽屉式站内通知能力。

具体底层通知实现是否为 Kafka，以及应复用哪个现有模块，需要结合当前项目代码确认，不在 requirements.md 中提前写死。

## 16. 测试平台与全研发流程平台的数据同步

为避免“开发计划时间”和“开发实际时间”混淆，本文件统一使用以下名称：

- **开发计划预期完成时间**：研发计划阶段预计完成开发的时间；用于“待介入 → 测试计划”的条件判断。
- **开发实际完成时间**：研发真正完成开发的实际时间；用于点击“开始测试执行”时的前置校验。

### 16.1 全研发流程平台 → 测试平台

至少包括：

| 事件 | 主要数据 |
|---|---|
| 需求进入 INT | `parentWfinstCode`（总需求编号）、`name1`（需求名称）、需求类型、`dmpNum`（需求编号）、业务需求 ZIP 链接（如有） |
| 同一总需求追加需求编号 | `parentWfinstCode`、`name1`、新的 `dmpNum` |
| 需求规格说明书 | 规格说明书信息/链接、`dmpNum` |
| 开发计划预期完成 | 开发计划预期完成时间、`dmpNum` |
| 开发实际完成 | 开发实际完成时间、`dmpNum` |

说明：

1. 全研发流程平台发送所有系统的数据，但不传“所属系统”。
2. 测试平台根据 `dmpNum` 按最长前缀匹配本地所属系统映射，只接入匹配到已启用指定系统的数据。
3. 未匹配或映射未启用的数据记录为已过滤，不创建目录和测试计划；补齐映射后允许人工重试。
4. 系统负责人审核属于全研发流程平台内部业务，测试平台不接收也不处理审核状态。
5. 同一 `dmpNum` 的重复消息不得导致重复创建测试计划。
6. 对同一 `dmpNum` 后续发送的规格说明书、计划时间、实际时间和允许更新的需求名称等字段按补充/更新处理。
7. `parentWfinstCode`、`dmpNum`、`name1` 分别固定映射为总需求编号、需求编号、需求名称；其他消息字段、messageType、Topic、接口形式仍由后续技术设计和联调确认。
8. 独立的需求撤回、需求取消等非主流程事件当前不推进或回退新版 INT 状态，相关处理留待后续版本确认。

### 16.2 测试平台 → 全研发流程平台

至少包括：

| 事件 | 主要数据 |
|---|---|
| 审批通过后的测试计划 | 最新有效准备/执行计划及人员；整体计划周期取最早准备开始时间和最晚执行结束时间 |
| 审批通过后的测试计划调整 | 最新有效计划时间、人员、调整原因 |
| 实际准备时间 | 实际准备开始时间、实际准备结束时间 |
| 实际执行时间 | 实际执行开始时间、实际执行结束时间 |
| 办结 | 办结状态、实际执行结束时间、报告链接、必要统计 |

除已经明确的 `parentWfinstCode`、`dmpNum`、`name1` 字段语义外，其余消息字段、messageType、Topic、接口形式等属于后续技术设计，不在本 requirements.md 中提前固定。

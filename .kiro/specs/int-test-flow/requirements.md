# INT 测试平台整体需求规格

> 本文件覆盖本次 INT 测试平台改造的整体需求，从全研发流程平台需求进入测试平台开始，到测试计划办结结束。
> 本文件只描述需求、业务规则和可验证行为，不提前固化数据库、接口实现、消息中间件、算法等技术方案。
> 已明确的规则直接写入需求；仍存在业务或技术不确定性的内容统一放在“待确认/待技术评估”章节。
>
> **需求解释优先级：本 requirements.md 为当前 INT 测试平台业务需求基线。历史 `.kiro/specs`、旧需求文档及现有代码仅用于字段、兼容性和技术实现参考；当其内容与本文件冲突时，以本文件为准。现有代码结构不得反向约束或修改本文件中已经明确的业务需求。**

---

## 1. 总体目标

本次改造以“测试计划”为核心业务对象，把需求接入、人员排期、测试准备、用例、缺陷、测试执行、报告和办结串成一条完整 INT 测试主线。

主状态链统一为：

```text
待介入 → 测试计划 → 待审批 → 待测试准备 → 测试准备 → 待测试执行 → 测试执行 → 办结
```

总体原则：

1. 测试计划是 INT 测试过程的主业务对象。
2. 功能用例、缺陷、评审结果、实际时间、报告都围绕测试计划展开。
3. 状态不允许任意跳转，当前状态只允许进入合法的下一状态。
4. 自动流转只在明确条件满足时发生；需要记录真实开始/结束时间的节点由人员主动操作。
5. 全研发流程平台负责提供需求和开发相关信息；测试平台负责 INT 测试过程本身。
6. 全研发流程平台收到 INT 办结后进入什么后续流程，不属于本次测试平台需求范围。
7. 系统负责人审核、确认等动作属于全研发流程平台内部流程，不纳入测试平台状态和业务规则。

## 2. 总需求编号、需求编号、所属系统与目录关系

测试平台目录结构为：

```text
所属系统
└─ 总需求编号-需求名称
   └─ 测试计划数据
```

### 2.1 总需求编号与需求编号的关系

1. “总需求编号”用于标识一条原始需求，是跨系统的上层业务标识。
2. 一条原始需求可以涉及多个系统，因此一个总需求编号可以关联多个需求编号。
3. “需求编号”用于标识原始需求落到具体系统后的系统需求，是测试计划需要保存的业务字段。
4. 业务需求在全研发流程平台创建后，涉及的系统及各系统对应的需求编号已经确定；后续各系统负责人审核属于全研发流程平台内部流程，与测试平台无关。
5. 需求编号的前缀能够确定所属系统，不同系统使用固定的需求编号前缀。
6. “需求编号前缀 ↔ 所属系统”的对应关系为固定映射，由测试平台维护。
7. 全研发流程平台不会向测试平台传入“所属系统”字段，测试平台收到需求编号后，应根据需求编号前缀和本地维护的映射关系确定所属系统。
8. 同一总需求编号下，不同需求编号可以分别归属不同系统，并分别形成对应系统目录下的测试计划数据。

业务关系可理解为：

```text
总需求编号（原始需求）
├─ 需求编号 A → 前缀映射 → 所属系统 A → 测试计划数据
├─ 需求编号 B → 前缀映射 → 所属系统 B → 测试计划数据
└─ 需求编号 C → 前缀映射 → 所属系统 C → 测试计划数据
```

### 2.2 系统映射维护

测试平台需要维护用于 INT 流程识别和人员匹配的系统基础映射，业务关系至少包括：

```text
需求编号前缀
    ↓
所属系统
    ↓
测试组/用户组
```

要求：

1. 需求编号前缀与所属系统的映射由测试平台维护，不依赖全研发流程平台传入所属系统。
2. 每个可进入 INT 的需求编号前缀应能唯一匹配到一个所属系统。
3. 所属系统可继续关联测试组/用户组，用于后续测试人员通知和计划处理。
4. 映射关系的具体维护页面、数据库结构及与 MeterSphere 现有项目/模块配置的兼容方式属于技术设计内容，不在本文件固定。

### 2.3 目录规则

1. “所属系统”由测试平台根据需求编号前缀映射得到，并据此创建或定位对应目录。
2. “总需求编号-需求名称”根据全研发流程平台传入的原始需求信息自动创建或定位。
3. 上述两级属于系统自动创建的业务目录层级。
4. 当前不额外增加禁止人工修改、移动或重命名的强制限制。
5. “需求编号”是测试计划数据的业务字段，不作为目录层级。
6. 同一“所属系统 + 总需求编号”下面允许存在多条测试计划数据，不按一对一关系限制。

### 2.4 原始需求类型

原始需求目前包括：

- 原始业务需求
- 系统优化需求

原始业务需求可携带业务需求 ZIP 包链接。

## 3. 需求接入与测试计划数据创建

### 3.1 需求进入测试平台

全研发流程平台向测试平台传入可进入 INT 的需求数据时，当前至少需要包含：

- 总需求编号
- 需求名称
- 需求类型
- 需求编号
- 原始业务需求的业务需求 ZIP 包链接（如有）

全研发流程平台不传“所属系统”。测试平台收到数据后：

1. 读取需求编号前缀，根据测试平台维护的固定映射关系确定所属系统。
2. 创建或定位该“所属系统”目录。
3. 在所属系统下创建或定位“总需求编号-需求名称”目录。
4. 在该目录下自动创建对应的测试计划数据。
5. 测试计划数据初始状态为“待介入”。
6. 需求编号保存为测试计划业务字段。
7. 此时等待需求规格说明书和开发计划预期完成时间等外部字段继续补齐。

系统负责人是否已审核、审核顺序以及全研发流程平台内部如何控制发送时点，不作为测试平台判断条件。测试平台只处理全研发流程平台实际发送并可进入 INT 的需求数据。

### 3.2 同一总需求下多个需求编号分批进入

同一总需求编号下可以存在多个需求编号，不同需求编号可以分批进入测试平台。

当测试平台后续收到同一总需求编号下新的需求编号时：

1. 根据新需求编号前缀映射出对应所属系统。
2. 创建或定位该系统对应的“所属系统”目录。
3. 在该系统下创建或定位相同“总需求编号-需求名称”目录。
4. 按新的需求编号创建对应测试计划数据。
5. 不影响同一总需求编号下已经存在的其他系统或其他需求编号对应的测试计划数据。

### 3.3 重复同步与后续字段更新

为避免外部平台重试、重复发送造成重复业务数据，需要满足以下业务结果：

1. 同一需求编号重复同步时，不得重复创建新的测试计划数据。
2. 测试平台应识别已经存在的需求编号，并将后续允许更新的外部字段更新到原测试计划数据或其 INT 扩展数据中。
3. 需求规格说明书、开发计划预期完成时间、开发实际完成时间等后续消息属于同一需求编号的字段补充或更新，不重新创建测试计划。
4. 同一总需求编号下出现新的需求编号时，才按新的系统需求创建新的测试计划数据。
5. 幂等键、唯一索引、消息 ID、重试机制等具体技术实现由 design.md 定义。
6. `【待确认】` 全研发流程平台后续修改“需求名称”时，测试平台已自动创建的“总需求编号-需求名称”目录是否同步重命名。

### 3.4 待介入数据补充

进入“待介入”后，以下信息可以分开到达：

- 需求规格说明书链接
- 开发计划预期完成时间

当两项同时存在时，测试计划自动从：

```text
待介入 → 测试计划
```

不得因为只收到其中一项而提前进入“测试计划”。

进入“测试计划”时，同时通知匹配到的测试组成员。

## 4. 测试计划状态机

### 4.1 状态链

```text
待介入
→ 测试计划
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

### 4.2 状态流转要求

1. 当前状态只展示合法下一状态或合法操作。
2. 自动流转节点不允许人员手工跳转。
3. “待介入 → 测试计划”为条件满足后的自动流转。
4. “测试计划 → 待审批”为提交测试计划后的人工操作。
5. “待审批 → 待测试准备/测试计划”为审批结果触发。
6. “待测试准备 → 测试准备”必须由人员点击“开始测试准备”。
7. “测试准备 → 待测试执行”必须由人员点击“完成测试准备”。
8. “待测试执行 → 测试执行”必须由人员点击“开始测试执行”。
9. “测试执行 → 办结”必须满足办结校验后由人员操作。
10. 人工开始/完成动作需要记录对应实际时间。
11. 冒烟测试不作为独立主状态。

### 4.3 状态与操作角色

当前状态操作责任按以下业务角色理解：

| 当前状态/动作 | 主要操作角色 | 说明 |
|---|---|---|
| 待介入 | 系统自动 | 等待外部字段补齐，不允许人工强制跳转 |
| 测试计划编制、提交 | 测试团队负责人 | 编制准备/执行排期并提交审批 |
| 待审批：通过/驳回 | 测试总负责人 | 审批发生在测试平台 |
| 开始测试准备 | 测试人员 | 记录实际准备开始时间 |
| 完成测试准备 | 测试人员 | 填写线下评审信息并上传评审后用例 |
| 开始测试执行 | 测试人员 | 先校验开发实际完成时间 |
| 测试执行、缺陷处理、办结 | 具备对应权限的测试人员 | 办结必须满足后端校验 |

具体 MeterSphere 权限点、角色绑定方式和多人场景由 design.md 设计；业务角色权限不得突破本状态机允许的流转范围。

## 5. 测试计划编制

### 5.1 准备与执行分别排期

测试准备人员与测试执行人员允许不同，分别维护计划安排。

测试准备安排至少包括：

- 执行人
- 计划准备开始日期
- 计划准备结束日期

测试执行安排至少包括：

- 执行人
- 计划执行开始日期
- 计划执行结束日期

要求：

1. 同一阶段支持多人，可通过多行分别维护。
2. 每个人单独维护自己的开始日期和结束日期。
3. 准备人员和执行人员可以完全不同。
4. 同一人员也可以同时参与准备和执行。
5. 当前计划编制页面中的可填写项均按必填处理。
6. 是否需要冒烟测试使用单选方式选择。

### 5.2 测试计划页面字段控制

测试计划编制时：

1. 负责人置灰，不允许在当前计划编制动作中修改。
2. 计划名称置灰，不允许在当前计划编制动作中修改。
3. 需求编号作为测试计划业务字段展示/保存。
4. 隐藏 MeterSphere 原“测试阶段”下拉框，不作为本次 INT 主流程的操作入口。
5. `【待确认】` 测试计划名称的自动生成来源及命名规则。
6. `【待确认】` 测试计划负责人自动赋值来源；需要明确其是否来源于所属系统对应测试组、固定测试团队负责人或其他规则。

### 5.3 整体计划时间

当计划中存在多名准备人员和执行人员时：

- 整体测试准备开始时间取所有准备安排中的最早开始时间。
- 整体测试执行结束时间取所有执行安排中的最晚结束时间。
- 对外同步整体计划周期时，使用“最早测试准备开始时间 + 最晚测试执行结束时间”。

### 5.4 提交测试计划

测试团队负责人完成计划编制后提交，状态从：

```text
测试计划 → 待审批
```

提交后等待测试总负责人审批。

## 6. 测试计划审批

测试计划审批在测试平台完成，不在全研发流程平台完成。

测试总负责人审批后：

- 审批通过：`待审批 → 待测试准备`
- 审批驳回：`待审批 → 测试计划`

审批要求：

1. 审批通过和审批驳回均可以填写审批意见。
2. 审批意见当前均不强制必填。
3. 审批驳回后，测试团队负责人可以根据意见修改计划后再次提交。
4. 审批通过后，测试平台向全研发流程平台同步最新有效测试计划信息。

## 7. 人员排期、空闲时间与冲突统计

人员排期能力需要同时解决两个问题：

1. 编制计划前能看出谁有空。
2. 保存计划时能发现人员是否与其他计划冲突。

### 7.1 冲突判断规则

编制或调整测试计划时，系统应检查执行人在目标日期范围内是否已被其他测试计划占用。

规则如下：

1. 查询该人员在其他“未办结”测试计划中的最新有效排期。
2. 测试准备排期和测试执行排期统一参与人员占用判断。
3. 按自然日期区间是否重叠判断冲突。
4. 不考虑法定节假日、调休、补班。
5. 暂不处理半天级冲突。
6. 暂不处理小时级冲突。
7. 暂不计算复杂负载百分比。
8. 存在冲突时明确提示，但允许继续保存测试计划。
9. 冲突提示应能看到相关测试计划、阶段和冲突日期范围。

### 7.2 人员排期统计

测试平台需要提供独立的人员排期统计能力，用于负责人在编制计划前按人员空闲情况划分任务。

用户可以指定统计日期范围，系统至少应统计和展示：

- 人员
- 已占用日期/天数
- 空闲日期/天数
- 冲突日期/天数
- 已排测试计划数量
- 具体测试计划
- 所属系统
- 需求编号
- 阶段（测试准备/测试执行）
- 计划开始日期
- 计划结束日期

占用区间存在重叠时，需要先合并日期区间再计算已占用天数，不能简单把不同计划天数直接相加。

空闲日期应基于用户选择的统计日期范围减去已占用日期得到。

冲突日期是同一人员在同一天存在两个或以上计划排期的日期。

### 7.3 Excel 导出

人员排期统计需要支持导出 Excel。

导出内容至少包括：

- 人员
- 统计开始日期
- 统计结束日期
- 已占用天数
- 空闲天数
- 冲突天数
- 已排计划数
- 测试计划
- 需求编号
- 所属系统
- 阶段
- 计划开始日期
- 计划结束日期
- 是否冲突

## 8. 测试计划调整

需求变化后，不直接覆盖原测试计划排期，而是在原计划基础上新增**计划版本**。

```text
计划版本 V1（保留）
→ 新增计划版本 V2
→ 修改人员/时间
→ 填写调整原因
→ 计划版本 V2 成为最新有效计划
```

要求：

1. 原计划版本保留，不覆盖，不删除。
2. 每次调整形成新的计划版本。
3. 最新计划时间和调整原因同步给全研发流程平台。
4. 新增调整计划版本这个动作本身不立即通知测试人员。
5. 后续测试准备提醒、测试执行提醒、人员空闲统计和冲突判断均以最新有效计划版本为准。
6. 本节的“计划版本 V1/V2”仅指测试计划排期版本，与第 10 节可能存在的“评审后用例版本/最终用例版本”是两个不同概念。

## 9. 待测试准备与测试准备

### 9.1 准备提醒

到达最新有效计划的准备开始日期当天 09:00，提醒对应测试准备人员可以开始测试准备。

### 9.2 开始测试准备

测试人员在“待测试准备”状态点击“开始测试准备”后：

1. 状态进入“测试准备”。
2. 记录实际准备开始时间。

不得仅因为到达计划准备开始日期而自动进入“测试准备”。

### 9.3 完成测试准备

INT 用例在线下编写和评审，不使用 MeterSphere 原“用例评审”模块作为本次 INT 主流程入口。

测试人员点击“完成测试准备”时，需要：

1. 填写评审结果。
2. 填写评审人员。
3. 上传线下评审后用例文件。
4. 记录实际准备结束时间。
5. 状态从“测试准备”进入“待测试执行”。

## 10. 用例上传、最终用例与版本识别

### 10.1 当前实际使用方式

测试人员主要在本地 Excel 中维护用例，不要求在测试平台页面逐条编辑。

当前流程：

```text
完成测试准备时上传评审后用例
→ 测试执行期间继续在本地 Excel 中维护
→ 办结前上传最终实际用例
```

测试执行期间允许在本地：

- 新增用例
- 修改用例
- 删除用例
- 调整用例顺序
- 更新最终执行状态

### 10.2 最终用例状态

办结前最终实际用例只允许存在：

- 通过
- 跳过

不得存在：

- 未执行
- 不通过
- 阻塞

### 10.3 用例稳定标识原则

如果后续实现评审后版本和最终版本自动差异比对，必须满足以下原则：

1. Excel 行号不能作为用例身份。
2. 页面排序序号不能作为用例身份。
3. Excel 调整排序后不能影响同一条用例的识别。
4. 需要存在稳定且不随排序变化的用例标识。
5. 可评估复用现有全局功能用例编号，或新增“计划用例 ID”。
6. 如果新增计划用例 ID，该 ID 在用例整个生命周期内保持不变。
7. 页面展示序号与稳定用例 ID 必须是两个概念。

### 10.4 用例版本与差异比对

以下内容当前不作为已确定交付需求，先进行技术评估：

- 是否保存“评审后用例版本”和“最终用例版本”两个快照。
- 是否实现两个用例版本的自动差异比对。
- 当前 Excel 是否已有稳定唯一用例编号。
- 如果没有稳定编号，是否由平台增加并维护计划用例 ID。
- 平台生成的稳定 ID 如何带入测试人员本地 Excel，并在最终上传时保持不变。
- 最终 Excel 再次上传时，对已有用例采用覆盖、合并还是其他更新规则。
- 最终 Excel 中新增、删除和修改用例的识别规则。

在上述技术评估和业务确认完成前，design.md 不应自行假设最终 Excel 的覆盖/合并策略，也不得把 Excel 行号或排序作为用例身份依据。

## 11. 待测试执行与测试执行

### 11.1 执行提醒

到达最新有效计划的执行开始日期当天 09:00，提醒相关测试执行人员。

开发实际完成时间晚于计划执行开始日期时，不改变原计划提醒规则。

### 11.2 开始测试执行

测试人员在“待测试执行”状态点击“开始测试执行”时，系统必须校验全研发流程平台是否已经提供“开发实际完成时间”。

如果未提供：

- 弹窗提示“开发实际完成时间未提供，不能流转”。
- 状态继续保持“待测试执行”。

如果已经提供：

- 状态进入“测试执行”。
- 记录实际执行开始时间。

“开发实际完成时间”到达本身不得自动把状态推进到“测试执行”。

## 12. 冒烟测试

是否需要冒烟测试在测试计划编制阶段确定。

如果计划标记“需要冒烟测试”，正式执行用例前先进行冒烟测试。

冒烟测试属于测试执行阶段的前置过程，不单独增加主状态。

冒烟测试具体需要记录的结论、人员、时间、备注、关联缺陷等字段仍待确认。

## 13. 测试计划与缺陷

### 13.1 缺陷关系

缺陷以测试计划为主关联对象，具体测试计划用例为可选关联对象。

```text
测试计划
└─ 缺陷（必须属于测试计划）
   └─ 具体测试计划用例（可选）
```

要求：

1. 测试计划页面增加“关联缺陷”视图。
2. “关联缺陷”展示当前测试计划下的全部缺陷。
3. 全局“缺陷管理”页面继续保留。
4. 测试计划缺陷不是新建一套缺陷数据，只是在当前测试计划上下文中查看和操作全局缺陷数据。

### 13.2 从测试计划新增缺陷

在测试计划“关联缺陷”页面点击新增缺陷时：

1. 缺陷必须关联当前测试计划。
2. 不强制关联具体用例。
3. 用户可以选择某条测试计划用例作为次级关联。

因此环境、部署、数据、公共问题、冒烟问题等没有明确用例归属的缺陷，也可以正常归属于测试计划。

### 13.3 从具体用例新增缺陷

从某条测试计划用例中新增缺陷时：

1. 自动关联当前测试计划。
2. 自动关联当前测试计划用例。

### 13.4 解除用例关联

如果一个缺陷已经属于测试计划，并同时关联某条测试计划用例，则解除“缺陷-用例”关系时：

- 只解除具体用例关系。
- 缺陷仍然保留在当前测试计划中。

### 13.5 技术兼容确认

以下两项需要结合现有后端实现继续确认：

- 新增缺陷接口是否支持只关联测试计划、不传计划用例。
- 解除用例关联时是否能够保留测试计划关联。

## 14. 测试计划办结

办结动作发生在测试平台。

办结前必须由后端进行完整校验，不能只依赖前端按钮状态。

### 14.1 用例校验

最终实际用例只能为：

- 通过
- 跳过

存在以下任一状态时禁止办结：

- 未执行
- 不通过
- 阻塞

### 14.2 缺陷校验

当前测试计划关联的全部缺陷必须全部为：

```text
已关闭
```

只认“已关闭”。

存在任意非“已关闭”缺陷时禁止办结。

办结校验必须按测试计划维度查询全部缺陷，不能只汇总具体用例下的缺陷，否则会漏掉没有关联具体用例的计划级缺陷。

### 14.3 办结成功

校验通过后：

1. 完成报告生成/保存/分享。
2. 记录实际执行结束时间。
3. 测试计划状态进入“办结”。
4. 向全研发流程平台同步办结状态、实际执行结束时间和报告链接。

## 15. 消息通知

测试平台需要根据所属系统找到对应测试组，并向相关人员发送处理提醒。所属系统由需求编号前缀与测试平台维护的固定映射关系确定。

当前测试组按“用户组”理解。

通知至少用于：

- “待介入 → 测试计划”后通知匹配到的测试组成员。
- 最新有效计划准备开始日期当天 09:00 提醒准备人员。
- 最新有效计划执行开始日期当天 09:00 提醒执行人员。

优先考虑复用项目现有右上角抽屉式站内通知能力。

具体底层通知实现是否为 Kafka，以及应复用哪个现有模块，需要结合当前项目代码确认，不在 requirements.md 中提前写死。

## 16. 测试平台与全研发流程平台的数据同步

为避免“开发计划时间”和“开发实际时间”混淆，本文件统一使用以下名称：

- **开发计划预期完成时间**：研发计划阶段预计完成开发的时间；用于“待介入 → 测试计划”的条件判断。
- **开发实际完成时间**：研发真正完成开发的实际时间；用于点击“开始测试执行”时的前置校验。

### 16.1 全研发流程平台 → 测试平台

至少包括：

| 事件 | 主要数据 |
|---|---|
| 需求进入 INT | 总需求编号、需求名称、需求类型、需求编号、业务需求 ZIP 链接（如有） |
| 同一总需求追加需求编号 | 总需求编号、需求名称、新的需求编号 |
| 需求规格说明书 | 规格说明书信息/链接、需求编号 |
| 开发计划预期完成 | 开发计划预期完成时间、需求编号 |
| 开发实际完成 | 开发实际完成时间、需求编号 |

说明：

1. 全研发流程平台不传“所属系统”。
2. 测试平台统一根据需求编号前缀和本地维护的固定映射确定所属系统。
3. 系统负责人审核属于全研发流程平台内部业务，测试平台不接收也不处理审核状态。
4. 同一需求编号的重复消息不得导致重复创建测试计划。
5. 对同一需求编号后续发送的规格说明书、计划时间和实际时间等字段按补充/更新处理。

### 16.2 测试平台 → 全研发流程平台

至少包括：

| 事件 | 主要数据 |
|---|---|
| 审批通过后的测试计划 | 最新有效准备/执行计划及人员；整体计划周期取最早准备开始时间和最晚执行结束时间 |
| 测试计划调整 | 最新计划时间、人员、调整原因 |
| 实际准备时间 | 实际准备开始时间、实际准备结束时间 |
| 实际执行时间 | 实际执行开始时间、实际执行结束时间 |
| 办结 | 办结状态、实际执行结束时间、报告链接、必要统计 |

消息字段、messageType、Topic、接口形式等属于后续技术设计，不在本 requirements.md 中提前固定。

## 19. 本次明确不做的事情

当前阶段不要求：

1. 设计全研发流程平台在 INT 办结后的下一业务流程。
2. 处理或复刻全研发流程平台内部的系统负责人审核流程。
3. 删除 MeterSphere 原用例评审、全局缺陷管理等既有能力。
4. 为 INT 流程重新建设一套独立缺陷系统。
5. 建设复杂自动排班引擎。
6. 计算半天、小时级人员排期。
7. 计算复杂人员负载百分比。
8. 处理法定节假日、调休、补班等工作日日历。
9. 在技术评估完成前，把用例双快照和用例版本自动差异比对列为强制交付能力。

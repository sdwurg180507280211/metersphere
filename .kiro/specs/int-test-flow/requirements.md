# INT 测试平台整体需求规格

> 本文件覆盖本次 INT 测试平台改造的整体业务需求，从全研发流程平台需求进入测试平台、公共池归属、测试进度编制、审批、测试准备、测试执行、缺陷、报告到办结/取消结束。
> 本文件只描述业务规则、页面行为和可验证结果，不提前固化数据库、消息中间件、接口协议等技术实现。
> 当前业务基线以本文件为准；旧版 requirements、历史流程图、旧需求文档及现有代码仅作为实现参考。后续业务确认如有变化，应先更新本文件再调整 design.md 和代码。

---

## 1. 总体目标与术语

本次改造以 MeterSphere 现有 `test_plan` 为底层技术对象，但用户可见业务名称统一改为“测试进度”。

页面、菜单、标题、字段名和业务文案统一使用：

```text
测试进度
```

不再向业务用户展示“测试计划”作为新版 INT 主流程名称；底层 Java 类、数据库表、接口内部参数等技术对象可继续复用 `test_plan/TestPlan/planId`，不要求仅为改名而重构底层模型。

新版 INT 主状态链为：

```text
待介入
→ 测试进度
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

另增加异常终止状态：

```text
已取消
```

总体原则：

1. 测试进度是 INT 测试过程的主业务对象。
2. 功能用例、缺陷、评审、人员排期、实际时间、报告都围绕测试进度展开。
3. 正常状态不允许任意跳转，只允许进入当前业务规则定义的合法下一状态。
4. 测试平台不提供“退回待介入”功能。
5. 如果业务需求本身发生变化，由全研发流程平台重新创建新需求；原需求在测试平台进入“已取消”，新需求重新进入公共池并重新走完整流程。
6. 测试平台负责 INT 测试过程；全研发流程平台负责需求、系统主数据、开发计划和开发实际完成等上游信息。
7. 历史普通测试计划保持原状，不批量转换为新版 INT 测试进度。

## 2. 系统主数据、测试组与负责人

### 2.1 系统主数据同步

全研发流程平台维护全部系统主数据，并将全部系统同步到测试平台。

测试平台需要展示和维护每个系统的以下信息：

| 字段 | 维护方 | 说明 |
|---|---|---|
| 系统名称 | 全研发流程平台 | 测试平台同步保存/展示，不独立创建第二套名称 |
| 系统简称 | 全研发流程平台 | 用于根据需求编号识别所属系统 |
| 是否纳入 INT | 测试平台 | 测试平台维护后同步回全研发流程平台 |
| 测试组 | 测试平台 | 测试组等同于 MeterSphere 项目 |
| 测试组负责人 | 测试平台 | 乙方负责人，负责接活、派活、编制测试进度 |
| 总负责人 | 测试平台 | 甲方领导，负责审批，不参与具体测试执行 |

系统名称、简称由全研发流程平台负责增删改；测试平台同步全量系统并在此基础上补充 INT 测试属性。

测试平台修改“是否纳入 INT、测试组、测试组负责人、总负责人”等测试属性后，需要同步回全研发流程平台。

### 2.2 测试组

测试组等同于 MeterSphere 项目。

一个项目可以对应一个或多个所属系统，也可以有一个或多个测试组负责人。

业务关系示例：

```text
测试组/项目 A
├─ 系统 CMS
├─ 系统 CMS2.0
├─ 测试组负责人：负责人甲、负责人乙
└─ 总负责人：甲方领导 A
```

### 2.3 测试组负责人与总负责人

两种角色职责固定区分：

#### 测试组负责人

- 乙方角色。
- 负责测试任务承接、派活、测试进度编制和提交审批。
- 可以作为新建测试进度的默认负责人。
- 默认负责人不是强制负责人，当前测试进度负责人允许有权限人员修改。
- 一个测试组允许配置多个测试组负责人。

#### 总负责人

- 甲方领导角色。
- 不参与具体测试准备、执行和派活。
- 主要用于测试进度审批。
- 一个总负责人可以对应多个测试组和多个测试组负责人。
- 总负责人和测试组负责人两个角色业务上不会冲突，不使用同一个互斥枚举字段表达二选一关系。

### 2.4 多测试组负责人当前规则

当某个系统/测试组配置多个测试组负责人时，当前暂定：

```text
创建测试进度时默认取配置顺序中的第一个测试组负责人
```

该规则只作为当前阶段临时默认策略，后续仍需继续讨论是否改为显式“默认负责人”、认领或其他分配方式。

## 3. 总需求、需求编号与所属系统

### 3.1 上游字段

当前已确认的核心字段：

| 业务字段 | 上游字段 | 含义 |
|---|---|---|
| 总需求编号 | `parentWfinstCode` | 一条跨系统的原始需求标识 |
| 需求编号 | `dmpNum` | 原始需求落到具体系统后的系统需求编号 |
| 需求名称 | `name1` | 原始需求名称 |

要求：

1. 一个总需求可以关联多个需求编号。
2. 一个总需求可以涉及多个系统。
3. `dmpNum` 是测试平台识别同一具体需求和后续消息匹配的稳定业务键。
4. 后期需求规格说明书、开发计划时间、开发实际完成时间等更新，应按需求编号定位原测试进度，不依赖页面目录路径匹配。
5. 目录是展示和管理结构，需求编号才是业务匹配依据。

### 3.2 根据需求编号确定所属系统

测试平台在创建测试进度时已经获得需求编号，因此必须能够根据需求编号确定所属系统。

业务关系为：

```text
需求编号
→ 系统简称/编号规则匹配
→ 所属系统
→ 测试组（项目）
→ 测试组负责人
→ 总负责人
```

因此：

1. 所属系统在测试进度创建阶段已经确定。
2. 测试组、默认测试组负责人和总负责人也在创建阶段已经确定。
3. 后续人工“移动”只负责目录归档，不负责判断所属系统，也不负责决定负责人。
4. 任何后续消息都不得通过当前目录路径反推需求身份。

## 4. 公共池、目录与移动规则

### 4.1 公共池定位

所有进入新版 INT 流程的需求首先进入公共池。

公共池按总需求组织：

```text
公共池
└─ 总需求编号-需求名称
   ├─ 需求编号 A
   ├─ 需求编号 B
   └─ 需求编号 C
```

总需求目录右侧可以展示原始业务需求 ZIP 链接等上游资料，供测试组负责人了解需求背景。

### 4.2 测试进度只能在公共池首次创建

这是固定业务规则：

> 新版 INT 测试进度只能在公共池中首次创建。

要求：

1. 需求同步进入公共池后，由系统在公共池当前需求位置自动创建对应测试进度数据。
2. 在测试进度创建成功之前，不允许移动该需求。
3. 前端“移动”按钮在测试进度尚未创建时必须隐藏或置灰。
4. 不允许负责人仅根据 ZIP 内容提前把需求移出公共池，再等待系统到目标目录创建测试进度。
5. 测试进度创建成功后，需求才进入“可移动/待归属目录”的业务阶段。
6. 移动时迁移的是已经存在的“需求 + 测试进度及其关联关系”，不能重新创建第二个测试进度。

推荐页面提示：

```text
计划创建中/进度创建中 → 不允许移动
测试进度已创建         → 允许移动
```

### 4.3 移动到所属系统

当同一总需求涉及多个系统时，在总需求目录右侧下拉操作中提供“移动”。

操作流程：

1. 点击总需求目录右侧“移动”。
2. 选择本次需要移动的一个或多个具体需求编号。
3. 选择目标系统目录。
4. 系统校验目标系统是否与需求编号已确定的所属系统一致。
5. 校验通过后，在目标系统下创建或定位“总需求编号-需求名称”目录。
6. 将选中的具体需求及其已创建测试进度移动到该目录。
7. 未被选中的其他需求继续留在公共池或原目录，不受影响。

例如：

```text
公共池
└─ Z202609001-客户服务能力优化
   ├─ CMS-001
   ├─ ACRM-001
   └─ Itrain-001
```

可分别移动为：

```text
CMS
└─ Z202609001-客户服务能力优化
   └─ CMS-001

ACRM
└─ Z202609001-客户服务能力优化
   └─ ACRM-001
```

如果目标系统下已经存在同一“总需求编号-需求名称”目录，则直接放入现有目录，不重复创建第二个总需求目录。

### 4.4 移动与业务归属分离

需要明确：

```text
所属系统、测试组、负责人
在创建测试进度时已经确定

目录移动
只是页面组织和归档动作
```

因此即使尚未完成目录移动，系统也已经知道该测试进度属于哪个系统、哪个测试组、默认负责人和总负责人。

## 5. 需求接入与测试进度创建

### 5.1 创建条件与结果

进入 INT 公共池的具体需求按 `dmpNum` 创建唯一测试进度。

创建时至少完成：

1. 保存总需求编号、需求编号和需求名称。
2. 根据需求编号确定所属系统。
3. 根据所属系统确定测试组。
4. 读取系统配置中的测试组负责人和总负责人。
5. 创建测试进度底层 `test_plan` 数据。
6. 默认负责人取当前系统配置中的测试组负责人；多负责人时当前暂取第一个。
7. 测试进度初始状态为“待介入”。
8. 测试进度首次创建位置必须在公共池对应的总需求目录中。
9. 创建成功后才开放“移动”操作。

测试进度负责人允许后续人工修改，不因系统默认负责人而强制锁死。

### 5.2 重复同步

1. 同一 `dmpNum` 重复同步时不得重复创建第二个测试进度。
2. 后续需求规格说明书、开发计划预期完成时间、开发实际完成时间等均更新原测试进度。
3. 同一总需求新增新的 `dmpNum` 时，按新需求编号新增一条独立测试进度。
4. 不根据测试进度名称或目录名称判断重复。

### 5.3 待介入数据补充

进入“待介入”后，以下信息可以分开到达：

- 需求规格说明书链接。
- 开发计划预期完成时间。

当两项同时存在时，测试进度自动从：

```text
待介入 → 测试进度
```

只收到其中一项时仍保持“待介入”。

目录是否已经从公共池移动到所属系统，不改变需求编号、所属系统、测试组和负责人的业务归属。

## 6. 测试进度状态机

### 6.1 正常状态链

新版 INT 页面只展示：

```text
待介入
→ 测试进度
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

“测试进度”字段用于展示当前所处状态。

### 6.2 已取消

“已取消”是异常终止状态，不属于正常下一节点。

当业务需求发生变化时：

1. 测试平台不允许将原测试进度退回“待介入”。
2. 全研发流程平台重新提出新需求并生成新的需求编号。
3. 原需求在测试平台进入“已取消”。
4. 新需求重新进入公共池并重新创建新的测试进度。

进入“已取消”后：

- 停止占用测试人员排期。
- 取消尚未发送的准备/执行提醒。
- 停止后续每日催办。
- 禁止继续测试准备、测试执行、审批和办结。
- 历史排期保留。
- 审批历史保留。
- 用例保留。
- 缺陷保留。
- 报告和操作记录保留供追溯。

已取消数据不得物理删除以代替业务取消。

### 6.3 正常流转

1. “待介入 → 测试进度”：规格说明书和开发计划预期完成时间齐全后自动流转。
2. “测试进度 → 待审批”：测试组负责人完成编制并提交。
3. “待审批 → 待测试准备”：总负责人审批通过。
4. “待审批 → 测试进度”：总负责人审批驳回。
5. “待测试准备 → 测试准备”：人员主动点击开始测试准备。
6. “测试准备 → 待测试执行”：完成评审登记且评审用例导入成功。
7. “待测试执行 → 测试执行”：人员主动开始执行且开发实际完成时间已存在。
8. “测试执行 → 办结”：办结校验全部通过后人工办结。
9. 冒烟测试不单独增加主状态。
10. 不提供任意状态手工跳转和“退回待介入”。

## 7. 测试进度编制与人员排期

### 7.1 基础信息

编制页面至少展示：

- 总需求编号。
- 需求编号。
- 需求名称。
- 所属系统。
- 测试组。
- 测试组负责人。
- 总负责人。
- 当前测试进度负责人。
- 需求规格说明书。
- 开发计划预期完成时间。
- 开发实际完成时间。
- 是否需要冒烟测试。

其中：

1. 当前测试进度负责人创建时默认取测试组负责人。
2. 默认负责人允许人工修改，不置灰为强制值。
3. 所属系统、测试组、测试组负责人、总负责人来源于系统配置关系。
4. 测试组负责人负责派活和提交审批；总负责人只负责审批，不承担具体测试执行工作。

### 7.2 准备和执行分别排期

测试准备安排至少包括：

- 执行人。
- 计划准备开始日期。
- 计划准备结束日期。

测试执行安排至少包括：

- 执行人。
- 计划执行开始日期。
- 计划执行结束日期。

要求：

1. 同一阶段支持多人。
2. 每个人单独维护开始日期和结束日期。
3. 准备人员与执行人员允许不同。
4. 同一人员可以同时参与准备和执行。
5. 保存/提交时检查与其他未办结测试进度的人员排期冲突。
6. 冲突明确提示，但当前允许继续保存/提交。
7. 不计算半天、小时级冲突和复杂负载百分比。

### 7.3 人员排期统计

至少支持按日期范围查看：

- 人员。
- 已占用日期/天数。
- 空闲日期/天数。
- 冲突日期/天数。
- 已排测试进度数量。
- 测试进度。
- 所属系统。
- 需求编号。
- 阶段（测试准备/测试执行）。
- 计划开始和结束日期。

支持 Excel 导出。

“已取消”测试进度不再占用人员排期，但历史排期仍可在历史记录中查询。

## 8. 审批与测试进度调整

### 8.1 V1 审批

测试组负责人完成首次编制后提交：

```text
测试进度 → 待审批
```

由对应总负责人审批。

审批结果：

- 通过：`待审批 → 待测试准备`
- 驳回：`待审批 → 测试进度`

审批通过和驳回均保存操作人、时间和审批意见；审批历史不得被后续结果覆盖。

### 8.2 排期/人员调整

业务需求本身发生变化时，不在原测试进度内做版本调整，而是由全研发流程平台重新提需求，原需求进入“已取消”。

如果需求本身不变，仅测试人员、测试准备日期、测试执行日期等排期发生调整，可以在同一测试进度下保留 V1/V2/V3 等调整版本。

规则：

1. 原有效版本保留，不覆盖、不删除。
2. 调整版本审批通过前，当前有效版本继续生效。
3. 调整版本审批通过后，新版本成为最新有效版本。
4. 调整版本驳回后，原有效版本继续生效。
5. 后续提醒、人员占用和对外同步以最新有效版本为准。
6. 日期调整后必须取消原日期尚未发送的提醒，并按新有效日期重新计算提醒。

## 9. 测试准备与评审

### 9.1 开始测试准备

达到最新有效准备开始日期后，由测试人员主动点击“开始测试准备”：

1. 状态从“待测试准备”进入“测试准备”。
2. 记录实际准备开始时间和实际操作人。
3. 到达计划日期本身不自动流转状态。

### 9.2 完成测试准备

INT 用例主要在线下 Excel 中编写并完成线下评审。

点击“完成测试准备”时，至少登记：

- 评审结果：通过/不通过。
- 评审人员。
- 评审意见。
- 评审后用例 Excel。

规则：

1. 评审通过时，评审人员必填、Excel 必填，评审意见可选。
2. 评审不通过时，评审人员必填、评审意见必填，Excel 可不上传。
3. 评审不通过继续保持“测试准备”，后续可重新评审；每轮评审完整留痕。
4. 评审通过后必须先完成 Excel 校验和结构化导入；导入失败不能进入“待测试执行”。
5. 第一次评审通过且导入成功的数据作为首次评审后用例基线。

## 10. Excel 用例标签、基线与最终用例

### 10.1 标签为用例稳定标识

新版 INT Excel 用例以“标签”作为同一测试进度内的稳定用例标识。

示例：

```text
标签    用例名称
L001    正常登录
L002    密码错误
L003    用户锁定
```

固定规则：

1. Excel 必须包含“标签”列。
2. 每条用例标签必须有值。
3. 标签在同一个测试进度内必须唯一。
4. 不同需求/不同测试进度之间允许重复使用 `L001`、`L002` 等标签。
5. 同一测试进度内出现重复标签时整批导入失败。
6. 缺少标签列或存在空标签时整批导入失败。
7. Excel 行号和页面排序不能作为用例身份。
8. 平台不再为缺失标签的用例自动生成稳定计划用例 ID。

### 10.2 首次评审后用例基线

第一次“评审通过 + Excel 校验成功 + 结构化导入成功”的用例数据保存为固定基线。

后续最终用例比对始终以该固定基线为准，不覆盖基线。

### 10.3 最终实际用例

测试执行期间允许在本地 Excel：

- 新增用例。
- 修改用例。
- 删除用例。
- 调整顺序。
- 更新执行结果。

办结前上传最终 Excel。

最终 Excel 同样必须满足标签必填和同一测试进度内唯一。

差异识别按标签完成：

| 差异类型 | 识别规则 |
|---|---|
| 新增 | 最终 Excel 中存在、基线中不存在的标签 |
| 删除 | 基线中存在、最终 Excel 中不存在的标签 |
| 修改 | 标签相同，但纳入比较的用例定义字段发生变化 |

单纯调整 Excel 行顺序不算修改。

如果测试人员改变一条已有用例的标签，系统无法再把它识别为原标签用例，因此当前按“原标签删除 + 新标签新增”处理；后续如业务希望支持标签改名，需要另行定义规则。

### 10.4 办结前用例状态

最终实际用例只允许：

- 通过。
- 跳过。

以下状态存在任一条时禁止办结：

- 未执行。
- 不通过。
- 阻塞。

## 11. 待测试执行、测试执行与冒烟

### 11.1 开始测试执行

测试人员点击“开始测试执行”时必须校验全研发流程平台是否已经提供开发实际完成时间。

如果未提供：

- 提示“开发实际完成时间未提供，不能流转”。
- 状态保持“待测试执行”。

如果已经提供：

- 状态进入“测试执行”。
- 记录实际执行开始时间和操作人。

开发实际完成时间到达本身不自动推进状态。

### 11.2 冒烟测试

是否需要冒烟在测试进度编制时确定。

冒烟属于“测试执行”阶段内部的前置过程，不新增主状态。

至少记录：

- 通过/不通过。
- 实际执行人。
- 执行时间。
- 备注。
- 关联缺陷（如有）。

需要冒烟时，最近一次冒烟未通过前禁止正式执行用例；冒烟失败后允许修复并再次冒烟，每轮结果保留历史。

## 12. 缺陷

缺陷继续复用 MeterSphere 现有缺陷数据，测试进度只是增加当前测试进度上下文。

关系：

```text
测试进度
└─ 缺陷（必须属于测试进度）
   └─ 具体用例（可选）
```

要求：

1. 测试进度页面增加“关联缺陷”视图。
2. 从测试进度直接新增缺陷时，必须关联当前测试进度，不强制关联具体用例。
3. 从具体用例新增缺陷时，同时关联当前测试进度和该用例。
4. 解除用例关联时，只解除具体用例关系，缺陷仍保留在测试进度中。
5. “已取消”的测试进度历史缺陷保留可追溯，不允许因取消而删除。

## 13. 办结

办结前由后端完成完整校验。

至少满足：

1. 状态为“测试执行”。
2. 需要冒烟时，最近一次冒烟为通过。
3. 最终 Excel 已成功校验并结构化导入。
4. 已完成最终 Excel 与首次评审后基线的新增/删除/修改比对。
5. 最终测试用例只存在“通过/跳过”。
6. 当前测试进度全部缺陷达到允许办结状态。
7. 报告生成/保存成功。

当前缺陷允许办结状态：

```text
已关闭
或
已取消
```

办结成功后：

1. 记录实际执行结束时间。
2. 测试进度进入“办结”。
3. 向全研发流程平台同步办结结果、实际时间、报告链接和必要统计。

“已取消”和“办结”是两个不同终态；已取消需求不得再执行办结。

## 14. 消息通知与持续催办

### 14.1 测试准备提醒

以最新有效准备开始日期为准：

1. 计划开始日当天 09:00 首次提醒准备人员。
2. 如果到下一个自然日 09:00 仍未完成“开始测试准备”状态流转，则再次提醒。
3. 此后每天 09:00 重复提醒，直至进入“测试准备”。

### 14.2 测试执行提醒

以最新有效执行开始日期为准：

1. 计划开始日当天 09:00 首次提醒执行人员。
2. 如果到下一个自然日 09:00 仍未完成“开始测试执行”状态流转，则再次提醒。
3. 此后每天 09:00 重复提醒，直至进入“测试执行”。

### 14.3 提醒变更

1. 排期日期调整后，取消旧有效日期对应的尚未发送提醒和后续催办，按新有效日期重新计算。
2. 测试进度进入“已取消”后，取消所有未发送提醒并停止每日催办。
3. 状态已经完成对应流转后不得继续发送该阶段催办。
4. 当前按每天 09:00 执行，不额外区分法定节假日、调休和补班。

通知优先复用现有站内通知能力；具体底层实现由 design.md 评估。

## 15. 测试平台与全研发流程平台同步

### 15.1 全研发流程平台 → 测试平台

至少包括：

| 事件 | 主要数据 |
|---|---|
| 系统清单新增/修改/删除 | 系统名称、系统简称及上游系统标识 |
| 需求进入 INT | `parentWfinstCode`、`name1`、`dmpNum`、需求类型、业务需求 ZIP 链接（如有） |
| 需求规格说明书 | `dmpNum` + 规格说明书信息/链接 |
| 开发计划预期完成 | `dmpNum` + 开发计划预期完成时间 |
| 开发实际完成 | `dmpNum` + 开发实际完成时间 |
| 需求取消/废弃 | `dmpNum` + 取消/废弃信息 |

要求：

1. 测试平台同步全部系统主数据。
2. 测试平台根据需求编号确定所属系统，不依赖当前目录位置判断。
3. 同一 `dmpNum` 重复消息不得重复创建测试进度。
4. 需求取消/废弃后，原测试进度进入“已取消”，释放资源并停止提醒，但保留全部历史。

### 15.2 测试平台 → 全研发流程平台

至少包括：

| 事件 | 主要数据 |
|---|---|
| 系统 INT 属性更新 | 是否纳入 INT、测试组、测试组负责人、总负责人等测试属性 |
| 测试进度审批通过 | 最新有效人员和准备/执行排期 |
| 测试进度调整审批通过 | 最新有效人员、日期和调整原因 |
| 实际准备时间 | 实际准备开始/结束时间 |
| 实际执行时间 | 实际执行开始/结束时间 |
| 办结 | 办结状态、报告链接和必要统计 |

系统名称和简称仍以全研发流程平台主数据为来源；测试属性由测试平台维护并回传。

## 17. 待确认事项

以下内容当前仍需继续讨论，暂不扩展为更复杂业务规则：

1. 一个系统/测试组配置多个测试组负责人时，当前创建测试进度默认取第一个；后续是否增加显式“默认负责人”、认领机制或其他分配方式需继续确认。
2. 测试组负责人的配置是否最终完全落在项目成员管理，还是由独立“项目-所属系统-负责人”映射页面统一维护，需结合现有 MeterSphere 页面确定最终交互。
3. 总负责人是否允许每个系统配置多个甲方领导，以及多人情况下具体审批规则（任一人通过、指定人审批或会签）需后续确认。

## 19. 本次明确不做的事情

当前阶段不要求：

1. 让测试平台人工把未办结测试进度退回“待介入”。
2. 因业务需求变化直接覆盖原需求；业务变化必须由全研发流程平台重新提新需求，原需求进入“已取消”。
3. 因取消而物理删除历史排期、审批、用例、缺陷和操作记录。
4. 在测试进度创建成功之前允许将需求从公共池移出。
5. 通过目录路径识别同一需求或匹配后续消息。
6. 为 INT 重新建设一套独立缺陷系统。
7. 使用 Excel 行号、页面排序代替用例“标签”识别用例。
8. 为缺失标签的用例自动生成标签后继续导入。
9. 建设复杂自动排班引擎、小时/半天级冲突或复杂负载百分比。
10. 为业务名称“测试进度”的调整而重命名底层 `test_plan` 技术对象。
11. 批量把历史普通测试计划转换为新版 INT 测试进度。

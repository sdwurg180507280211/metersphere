# INT 测试平台整体需求规格

> 本文件为当前 INT 测试平台业务需求基线。
> 当前业务名称统一使用“测试进度”；底层继续复用 MeterSphere 现有 `test_plan/TestPlan/planId` 技术对象。
> 后续业务确认如有变化，应先更新本文件，再调整 design.md 和代码。

---

## 1. 总体目标与业务术语

新版 INT 主流程围绕“测试进度”展开。

用户可见名称统一为：

```text
测试进度
```

正常主状态链：

```text
待介入
→ 测试进度
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

另保留异常终止状态：

```text
已取消
```

固定原则：

1. “测试进度页面”就是现有 MeterSphere“测试计划页面”改名后的页面，不新增另一套详情页。
2. 用户可见菜单、页面标题、列表名称、字段名称和业务文案统一使用“测试进度”。
3. 底层继续复用 `test_plan` 技术对象，不因为业务改名而重命名表、Java 类或内部参数。
4. 历史普通测试计划保持原状，不批量转换为新版 INT 测试进度。
5. 正常主状态不允许任意跳转。
6. 状态名称“测试进度”当前继续保留，不改成“待编制”或“进度编制”。
7. 在测试平台业务上下文中，一条具体“需求”（`dmpNum`）同步后对应一条“测试进度”，也就是现有 MeterSphere 的一条“测试计划”；需求、测试进度、测试计划不是三套独立对象，而是同一个业务对象，底层对应同一条 `test_plan/planId`。
8. “总需求”（`parentWfinstCode`）仍是上游跨系统聚合和目录组织概念，不等同于一条具体 `test_plan`。

## 2. 系统主数据、项目、测试组负责人和总负责人

### 2.1 系统主数据来源

全部系统基础主数据由全研发流程平台维护，并通过 MQ 同步到测试平台。

全研发流程平台负责的基础字段至少包括：

- 系统标识。
- 系统名称。
- 系统简称。
- 系统新增、修改、删除/停用等主数据事件。

测试平台只同步这些基础系统主数据，不成为系统名称、系统简称的第二主数据源。

### 2.2 测试平台本地维护字段

测试平台在全部系统主数据基础上维护本地 INT 测试属性：

| 字段 | 维护方 | 说明 |
|---|---|---|
| 系统名称 | 全研发流程平台 | 测试平台同步保存/展示 |
| 系统简称 | 全研发流程平台 | 用于需求编号识别所属系统 |
| 项目/测试组 | 测试平台 | 测试组等同于 MeterSphere 项目 |
| 测试组负责人 | 测试平台 | 乙方负责人 |
| 总负责人 | 测试平台 | 甲方领导 |
| 是否纳入 INT | 测试平台 | 决定该系统需求是否进入 INT 流程 |

项目、测试组负责人、总负责人、是否纳入 INT 都是测试平台本地字段，全研发流程平台不负责维护这些字段。

这些本地测试属性由测试平台超级管理员维护。

### 2.3 组织关系

固定关系：

```text
一个总负责人
→ 可以负责多个项目

一个项目
→ 只属于一个总负责人
→ 可以包含多个系统

一个系统
→ 只属于一个项目
```

测试组等同于项目。

总负责人是甲方领导，负责审批和必要的管理调整，不参与具体测试准备、测试执行和日常派活。

测试组负责人是乙方负责人，负责测试任务承接、派活、编制测试进度、阶段推进和办结。

### 2.4 多测试组负责人

一个项目/测试组允许配置多个测试组负责人。

创建测试进度时，当前暂定：

```text
默认负责人 = 配置顺序中的第一个测试组负责人
```

该规则先作为当前实现口径保留；后续如业务需要，可再增加显式默认负责人或其他分配规则。

### 2.5 当前测试进度负责人调整

当前测试进度负责人创建时默认取测试组负责人。

后续允许：

- 总负责人修改当前测试进度负责人。
- 测试组负责人修改当前测试进度负责人。
- 负责人请假、换人等情况下可以随时调整。

当前负责人调整不要求等待业务需求变更规则确定。

## 3. 需求编号、所属系统与 INT 接入

### 3.1 核心上游字段

| 业务字段 | 上游字段 | 含义 |
|---|---|---|
| 总需求编号 | `parentWfinstCode` | 一条跨系统原始需求标识 |
| 需求编号 | `dmpNum` | 落到具体系统后的需求编号 |
| 需求名称 | `name1` | 原始需求名称 |

要求：

1. 一个总需求可以关联多个需求编号。
2. 一个总需求可以涉及多个系统。
3. `dmpNum` 是测试平台定位具体需求和后续消息的稳定业务键。
4. 需求规格说明书、开发计划预期完成时间、开发实际完成时间等后续消息均按 `dmpNum` 定位原测试进度。
5. 目录路径不作为业务匹配依据。

### 3.2 根据需求编号确定所属系统

需求编号前半段包含系统简称。

测试平台根据系统表中维护的系统简称映射关系识别所属系统。

业务链路：

```text
需求编号
→ 匹配系统简称
→ 所属系统
→ 所属项目/测试组
→ 测试组负责人
→ 总负责人
```

因此所属系统、项目、测试组负责人和总负责人在创建测试进度时已经可以确定，不依赖后续谁执行目录移动。

### 3.3 未纳入 INT 的系统

系统“是否纳入 INT = 否”时，该系统需求不进入 INT 测试流程：

- 不进入公共池。
- 不创建测试进度。
- 测试平台业务侧不保留该需求的 INT 记录。

上游是否提前过滤消息或测试平台消费后过滤，由 design.md 决定；业务结果必须一致。

### 3.4 无法匹配系统的异常需求

如果收到的需求编号无法根据系统简称匹配所属系统，视为全研发流程平台上游数据错误。

当前业务口径：

- 直接丢弃该条 INT 需求消息。
- 不进入公共池。
- 不创建测试进度。
- 不创建业务侧“待处理/接入异常”记录。

## 4. 公共池、测试进度创建与目录移动

### 4.1 公共池

所有进入新版 INT 流程的需求首先进入公共池。

公共池按总需求组织：

```text
公共池
└─ 总需求编号-需求名称
   ├─ 需求编号 A
   ├─ 需求编号 B
   └─ 需求编号 C
```

总需求目录右侧可以展示原始业务需求 ZIP 链接等上游资料。

### 4.2 测试进度只能在公共池首次创建

固定规则：

1. 需求进入公共池后，在公共池当前需求位置创建对应测试进度。
2. 测试进度创建成功之前，不允许移动需求。
3. 测试进度创建成功后才开放“移动”。
4. 移动时迁移已经存在的“需求 + 测试进度及其关联关系”，不得重新创建第二条测试进度。
5. 同一 `dmpNum` 重复同步不得重复创建第二条测试进度。

### 4.3 谁可以移动

公共池中的“移动”操作由测试组负责人执行。

### 4.4 移动目标

测试进度创建时所属系统已经确定。

移动时可以打开目标目录选择，但只能选择该需求已确定所属系统下的位置，不允许通过“移动”改变业务所属系统。

同一总需求涉及多个系统时，可以选择一个或多个具体需求编号分别移动到各自所属系统目录。

如果目标系统下已存在同一“总需求编号-需求名称”目录，则直接复用。

### 4.5 目录名称变化

总需求名称后续发生变化时：

- 已创建的“总需求编号-需求名称”目录不自动改名。
- 页面业务名称可以更新。
- 目录如需调整，由超级管理员手工修改。

系统名称、系统简称等主数据变化也不得自动迁移或重命名历史业务目录；旧数据关系保持不变。

## 5. 待介入与进入“测试进度”状态

测试进度初始状态为：

```text
待介入
```

从“待介入”自动进入“测试进度”必须同时满足三个条件：

1. 已收到需求规格说明书链接。
2. 已收到开发计划预期完成时间。
3. 需求已经从公共池移动到所属系统目录。

只有三项全部具备后：

```text
待介入 → 测试进度
```

少任意一项都继续保持“待介入”。

---

## 6. 测试进度状态机

### 6.1 正常状态链

```text
待介入
→ 测试进度
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

### 6.2 正常流转

1. `待介入 → 测试进度`：规格说明书、开发计划预期完成时间、目录移动三项条件同时满足后自动流转。
2. `测试进度 → 待审批`：测试组负责人完成编制并提交。
3. `待审批 → 待测试准备`：总负责人审批通过。
4. `待审批 → 测试进度`：总负责人审批驳回。
5. `待测试准备 → 测试准备`：第一个测试准备人员成功点击“开始准备”。
6. `测试准备 → 待测试执行`：全部准备人员结束后，由测试组负责人在状态列选择“待测试执行”，完成线上评审登记和评审后用例导入后流转。
7. `待测试执行 → 测试执行`：第一个测试执行人员成功点击“开始执行”，且开发实际完成时间已经存在。
8. `测试执行 → 办结`：全部执行人员结束后，由测试组负责人在状态列选择“办结”，办结校验全部通过后流转。

### 6.3 已取消

“已取消”保留为异常终止状态。

收到全研发流程平台明确的需求取消/废弃事件时，可以进入“已取消”。

当前暂不展开以下边界规则：

- 已办结后又收到取消/废弃消息如何处理。
- 取消时人员正在准备/执行且实际结束时间为空如何处理。

这些边界场景不作为当前开发固定规则。

## 7. 测试进度页面与人员安排

### 7.1 页面定义

“测试进度页面”就是现有 MeterSphere“测试计划页面”改名后的页面。

不新增“测试进度详情页”。

### 7.2 人员安排入口

测试进度页面提供：

```text
【人员安排】
```

点击后打开人员安排弹窗。

弹窗包含两个页签：

```text
测试准备
测试执行
```

### 7.3 测试准备人员字段

每名测试准备人员分别维护 4 个时间字段：

- 计划准备开始时间。
- 计划准备结束时间。
- 实际准备开始时间。
- 实际准备结束时间。

### 7.4 测试执行人员字段

每名测试执行人员分别维护 4 个时间字段：

- 计划执行开始时间。
- 计划执行结束时间。
- 实际执行开始时间。
- 实际执行结束时间。

同一人员同时参与测试准备和测试执行时，共有 8 个阶段时间字段；两套时间相互独立。

## 8. 个人开始/结束动作与实际时间

### 8.1 个人按钮

测试准备：

```text
开始准备
结束准备
```

测试执行：

```text
开始执行
结束执行
```

按钮状态：

- 实际开始为空：显示“开始准备/开始执行”。
- 实际开始有值、实际结束为空：显示“结束准备/结束执行”。
- 实际开始和实际结束均有值：显示“已完成”。

### 8.2 只能本人操作

个人“开始/结束”按钮只能由该测试人员本人操作。

测试组负责人、总负责人、管理员都不能替测试人员直接点击个人开始/结束按钮。

### 8.3 实际时间不可更正

个人点击按钮后，系统记录当前系统时间。

如果测试人员误点开始或结束，当前业务规则不提供更正功能，也不允许直接编辑实际时间。

### 8.4 允许提前开始和提前结束

测试人员可以在计划时间之前主动点击开始或结束。

例如计划准备为 9/20～9/22：

- 9/19 点击“开始准备”，实际准备开始记录为真实点击时间。
- 9/21 点击“结束准备”，实际准备结束记录为真实点击时间。

### 8.5 第一个人开始推动阶段开始

当整体状态为“待测试准备”时，第一个准备人员成功点击“开始准备”后：

```text
待测试准备 → 测试准备
```

其他准备人员后续开始只记录自己的实际时间。

当整体状态为“待测试执行”时，第一个执行人员成功点击“开始执行”且开发实际完成时间存在后：

```text
待测试执行 → 测试执行
```

其他执行人员后续开始只记录自己的实际时间。

### 8.6 提前实际结束释放剩余计划占用

人员产生实际结束时间后，该人员剩余计划占用立即释放。

例如计划结束为 9/25，实际在 9/23 完成：

```text
9/23 实际结束时间产生后
→ 9/24、9/25 不再继续占用该人员排期
```

人员空闲和冲突统计需要考虑该规则。

## 9. 整体实际时间口径

测试进度主对象不额外维护第二套可人工录入的整体实际时间。

整体时间统一由个人实际时间聚合计算。

### 9.1 测试平台内部聚合

```text
整体实际准备开始
= 所有准备人员实际准备开始时间的最早值

整体实际准备结束
= 所有准备人员实际准备结束时间的最晚值

整体实际执行开始
= 所有执行人员实际执行开始时间的最早值

整体实际执行结束
= 所有执行人员实际执行结束时间的最晚值
```

对应阶段尚有人未结束时，不视为已经形成完整的阶段整体实际结束时间。

### 9.2 同步给全研发流程平台

全研发流程平台当前只需要两个时间：

```text
测试开始时间
= 所有准备人员实际准备开始时间的最早值

测试结束时间
= 所有执行人员实际执行结束时间的最晚值
```

不要求向全研发流程平台同步每个人的准备/执行实际时间明细。

主状态变化仍独立记录状态流转时间、操作人和操作入口；状态流转时间不等于人员实际时间。

## 10. 测试准备结束、线下评审与进入待测试执行

### 10.1 所有准备人员必须结束

测试人员点击“结束准备”后，只记录本人实际准备结束时间。

当仍有任何当前有效测试准备人员未结束时：

- 整体状态继续保持“测试准备”。
- 状态列不能成功流转到“待测试执行”。

必须所有当前有效准备人员都已经产生实际开始和实际结束时间，才具备进入“待测试执行”的前置资格。

### 10.2 不自动流转

所有准备人员结束后：

- 主状态仍保持“测试准备”。
- 不自动进入“待测试执行”。
- 状态列下拉框开放合法下一状态“待测试执行”。

### 10.3 谁可以进入待测试执行

只有测试组负责人可以在状态列选择“待测试执行”。

总负责人不执行该业务动作。

### 10.4 选择待测试执行后的弹窗

测试组负责人在状态列选择“待测试执行”时，不立即改状态，而是打开测试准备完成弹窗。

弹窗至少包含：

- 评审结果。
- 评审人员。
- 评审意见。
- 评审后用例 Excel。

业务规则：

1. 用例在线下完成评审。
2. 线上只登记“评审通过”，不提供“评审不通过”业务分支。
3. 评审人员必填。
4. 评审后用例 Excel 必填。
5. 评审意见可选。
6. 系统再次校验所有准备人员已经结束。
7. Excel 校验和结构化导入全部成功后，才执行 `测试准备 → 待测试执行`。
8. 用户取消弹窗或 Excel 导入失败时，主状态继续保持“测试准备”。

不再额外设置一个与状态下拉重复的“完成测试准备”主按钮。

## 11. Excel 用例标签、基线和最终版本

### 11.1 标签规则

Excel 必须包含“标签”列。

固定规则：

1. 每条用例标签必须有值。
2. 同一测试进度内标签必须唯一。
3. 不同测试进度之间允许重复使用相同标签。
4. 标签格式不强制为 `L001/L002/L003`，只要求非空和唯一。
5. 导入时先对标签去除首尾空格。
6. 标签唯一性和后续比较不区分大小写。
7. 缺少标签列、存在空标签或规范化后重复标签时整批导入失败。
8. Excel 行号和页面排序不能作为用例身份。
9. 平台不为缺失标签的用例自动生成标签。

### 11.2 首次评审后用例版本

第一次线上登记评审通过且 Excel 校验、结构化导入成功的数据保存为首次评审后用例版本。

该版本作为后续差异比较基线，不被最终 Excel 覆盖。

### 11.3 最终用例版本

办结前上传最终 Excel。

最终 Excel 形成独立的最终用例版本。

要求：

- 首次评审后版本保留。
- 最终版本另存一版。
- 两个版本都保留，不互相覆盖。
- 不因为最终 Excel 删除某个标签而物理删除历史基线数据。
- 已有关联缺陷的历史用例关系继续可追溯。

差异比较按规范化后的标签完成：

| 差异类型 | 识别规则 |
|---|---|
| 新增 | 最终版本存在、基线不存在的标签 |
| 删除 | 基线存在、最终版本不存在的标签 |
| 修改 | 标签相同，但纳入比较的用例定义字段变化 |

标签改名当前按“原标签删除 + 新标签新增”处理。

### 11.4 办结前用例状态

最终实际用例只允许：

- 通过。
- 跳过。

存在以下任一状态时禁止办结：

- 未执行。
- 不通过。
- 阻塞。

## 12. 测试执行与冒烟

### 12.1 开始执行

测试人员点击“开始执行”时必须先校验开发实际完成时间。

如果开发实际完成时间不存在：

```text
开发实际完成时间未提供，不能开始测试执行
```

不写入个人实际执行开始时间，也不改变主状态。

如果已经存在：

- 记录该人员实际执行开始时间。
- 第一个成功开始执行的人触发 `待测试执行 → 测试执行`。

### 12.2 冒烟属于测试执行投入

冒烟测试属于测试执行阶段内部工作，不新增主状态。

冒烟消耗的时间属于测试执行实际投入，因此个人实际执行开始时间不需要等冒烟通过后才产生。

### 12.3 冒烟不通过

冒烟不通过时：

- 进入现有缺陷流转。
- 生成/关联阻塞类型缺陷。
- “阻塞”在这里作为缺陷类型/严重程度使用。
- 系统不因为该阻塞缺陷自动禁止其他测试人员继续执行，也不阻止其他用例继续执行。

因此当前不设置“冒烟未通过则全量禁止正式执行”的系统级门禁。

## 13. 缺陷

缺陷继续复用 MeterSphere 现有缺陷数据和现有“缺陷来源”字段，不新增一套平行的需求/测试进度/测试计划归属字段。

### 13.1 缺陷归属口径

在测试平台业务上下文中：

```text
具体需求
= 测试进度
= 测试计划
= 同一条 test_plan / planId
```

“缺陷来源”是缺陷主归属的事实字段，用来决定该缺陷绑定到哪一条具体需求/测试进度/测试计划。

因此：

- 不再把“需求”和“测试计划”理解为两个独立可选的缺陷归属对象。
- 不通过当前页面目录、需求名称文本或用例关联来推断缺陷主归属。
- 缺陷最终属于哪条需求/测试进度/测试计划，以现有“缺陷来源”字段指向的具体 `test_plan/planId` 为准。

### 13.2 创建和关联缺陷

1. 在某条需求/测试进度/测试计划上下文中新增缺陷时，“缺陷来源”必须填写并指向当前这条 `test_plan/planId`。
2. 页面已有当前测试进度上下文时，可以自动带出当前计划作为“缺陷来源”；保存时该字段不能为空。
3. 从具体用例新增缺陷时，同样必须把“缺陷来源”填写为该用例所属的当前 `test_plan/planId`；具体用例关系可以同时保存，但用例关系不决定缺陷主归属。
4. 在缺陷管理等没有当前测试进度上下文的位置新建缺陷时，必须通过现有“缺陷来源”字段选择具体需求/测试进度/测试计划。
5. 将已有缺陷关联到当前需求/测试进度/测试计划时，必须以现有“缺陷来源”字段确认或建立归属；不能再额外建立另一套独立的“计划-缺陷主归属”关系与“缺陷来源”并存。
6. 如果已有缺陷的“缺陷来源”指向其他 `test_plan`，则不能仅靠页面“关联”动作把它同时视为当前测试进度的缺陷；是否允许修改原缺陷来源，沿用现有缺陷字段编辑能力和权限规则，由 design.md 结合现有实现确定。

### 13.3 用例关联

用例关联是缺陷的附加关系，不是缺陷主归属关系。

例如：

```text
缺陷来源：当前 test_plan / planId
关联用例：L003（可选）
```

表示该缺陷属于当前需求/测试进度/测试计划，同时由 L003 用例发现或关联。

解除用例关联时，只解除具体用例关系，不改变“缺陷来源”，因此缺陷仍属于原需求/测试进度/测试计划。

### 13.4 测试进度页面的缺陷范围

测试进度页面的“关联缺陷”视图以现有“缺陷来源”字段为主要查询口径：

```text
缺陷来源指向当前 planId
→ 属于当前需求/测试进度/测试计划的缺陷
```

历史用例版本、用例关联和缺陷来源关系必须继续可追溯。

## 14. 办结

### 14.1 前置条件

所有当前有效测试执行人员必须已经产生实际执行结束时间，才允许进入办结流程。

### 14.2 谁可以办结

只有测试组负责人可以触发办结。

### 14.3 办结入口

“办结”放在状态列下拉框中。

测试组负责人选择“办结”后，不立即修改主状态，而是打开办结弹窗/执行办结校验。

### 14.4 办结校验

至少校验：

1. 当前主状态为“测试执行”。
2. 所有当前有效执行人员均已结束执行。
3. 最终 Excel 已成功校验并形成最终用例版本。
4. 已完成最终版本与首次评审后版本的新增/删除/修改比对。
5. 最终测试用例只存在“通过/跳过”。
6. 当前测试进度全部缺陷达到允许办结状态。
7. 报告生成/保存成功。

当前缺陷允许办结状态：

```text
已关闭
或
已取消
```

冒烟是否通过不再单独作为系统级办结门禁；冒烟失败产生的缺陷按正常缺陷状态参与办结校验。

全部校验成功后：

```text
测试执行 → 办结
```

## 15. 人员排期、空闲与冲突统计

测试准备和测试执行分别排期。

要求：

1. 同一阶段支持多人。
2. 每个人独立维护计划开始和计划结束时间。
3. 准备人员和执行人员可以不同。
4. 同一人员可以同时参与准备和执行。
5. 保存/提交时检查与其他未办结测试进度的人员排期冲突。
6. 冲突需要明确提示，但当前允许继续保存/提交。
7. 不处理半天、小时级排期和复杂负载百分比。

人员排期统计至少支持：

- 人员。
- 已占用日期/天数。
- 空闲日期/天数。
- 冲突日期/天数。
- 已排测试进度数量。
- 测试进度。
- 所属系统。
- 需求编号。
- 阶段。
- 计划开始/结束时间。
- 实际开始/结束时间。

实际结束时间一旦产生，立即释放该人员后续剩余计划占用。

支持 Excel 导出。

## 16. 站内通知与持续催办

### 16.1 时区

所有每天 09:00 的业务提醒统一按：

```text
Asia/Shanghai
```

不跟随浏览器或个人所在地时区变化。

### 16.2 通知按钮

通知中可以直接提供与“人员安排”弹窗相同的个人动作按钮：

- 开始准备。
- 结束准备。
- 开始执行。
- 结束执行。

通知按钮与页面按钮调用同一套后端业务校验。

通知本身、打开通知、查看通知都不能自动写实际时间或自动改变状态。

### 16.3 准备开始提醒

针对每名准备人员：

```text
到达计划准备开始日 09:00
且实际准备开始为空
→ 提醒“开始准备”
```

如果仍未开始，此后每天 09:00 继续提醒，直到实际准备开始时间产生。

提前开始后不再发送开始提醒。

### 16.4 准备结束提醒

针对每名准备人员：

```text
到达计划准备结束日 09:00
且实际准备开始已有值
且实际准备结束为空
→ 提醒“结束准备”
```

如果仍未结束，此后每天 09:00 继续提醒。

如果计划结束日到达时仍未开始，则继续提醒“开始准备”，不同时发送“结束准备”。

### 16.5 执行开始提醒

针对每名执行人员：

```text
到达计划执行开始日 09:00
且实际执行开始为空
→ 提醒“开始执行”
```

此后每天 09:00 催办，直到实际执行开始时间产生。

点击“开始执行”仍必须校验开发实际完成时间。

### 16.6 执行结束提醒

针对每名执行人员：

```text
到达计划执行结束日 09:00
且实际执行开始已有值
且实际执行结束为空
→ 提醒“结束执行”
```

此后每天 09:00 催办，直到实际执行结束时间产生。

### 16.7 提前结束

人员提前实际结束后：

- 立即停止该人员后续结束催办。
- 立即释放该人员剩余计划占用。

## 17. 平台间数据同步

### 17.1 全研发流程平台 → 测试平台

至少包括：

|---|---|

| 测试结束时间 | 所有执行人员实际执行结束时间最晚值 |

暂不要求同步：

- 每个人的实际准备时间明细。
- 每个人的实际执行时间明细。
- 测试平台本地维护的项目、测试组负责人、总负责人等测试属性。

## 18. 需求变更与版本机制：当前暂缓

业务需求发生变化时，究竟采用：

- 新增一个新需求并处理原需求；
- 还是修改原有需求；
- 是否需要 V2/V3 等版本；
- 已产生的人员实际时间如何与版本关联；

当前尚未最终确定。

因此：

1. 不再把“需求变更必须新建需求、原需求必须取消”写成当前固定业务规则。
2. 不把 V2/V3 需求变更版本机制作为当前已确认验收规则。
3. 与需求变更相关的历史版本、人员替换、日期重排等规则继续待业务确认。
4. 当前测试进度负责人因请假等原因被总负责人或测试组负责人直接调整，不等同于业务需求变更。

---

## 19. 当前暂不考虑的边界问题

以下问题当前明确暂不展开：

1. 已办结测试进度后又收到全研发取消/废弃消息的处理。
2. 需求取消时人员仍在准备/执行且实际结束为空的处理。
3. 业务需求变更采用新需求还是修改原需求，以及对应版本机制。
4. 更复杂的多人默认负责人分配机制。
5. 半天/小时级自动排班和复杂负载百分比。

---

## 20. 当前明确不做的事情

1. 不新增一套独立“测试进度详情页”。
2. 不为了“测试进度”业务名称重命名底层 `test_plan` 技术对象。
3. 不允许测试进度创建成功前将需求从公共池移出。
4. 不通过目录路径识别同一需求或匹配后续消息。
5. 不允许通过移动动作改变需求所属系统。
6. 不为未纳入 INT 的系统需求创建测试进度。
7. 不为无法匹配所属系统的需求创建公共池待处理数据。
8. 不允许他人代替测试人员点击个人“开始/结束”按钮。
9. 不提供误点个人实际时间后的更正功能。
10. 不因为到达计划开始/结束日期自动写入实际时间。
11. 不因为所有准备人员结束而自动进入“待测试执行”。
12. 不单独设置“完成测试准备”主按钮；阶段推进走状态列下拉框。
13. 不在线上提供“评审不通过”分支；用例评审在线下完成。
14. 不因为冒烟未通过而系统级禁止后续所有测试执行。
15. 不因为所有执行人员结束而自动办结；办结由测试组负责人从状态列发起。
16. 不使用 Excel 行号、页面排序代替标签识别用例。
17. 不强制标签必须使用 `L001` 等固定格式。
18. 不覆盖首次评审后用例版本和最终用例版本。
19. 不把尚未确认的需求变更/V2/V3 规则当成当前固定实现要求。
20. 不新增与现有“缺陷来源”并行的第二套需求/测试进度/测试计划主归属字段；缺陷主归属统一以现有“缺陷来源”字段为准。

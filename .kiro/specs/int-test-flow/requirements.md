# INT 测试流程需求

> 本文件用于当前阶段梳理 INT 测试平台需求，只描述业务逻辑与行为，不提前固化具体技术实现。
> 未确认内容统一标记为 `【待确认】`。

## 1. 核心对象与目录

### 1.1 核心对象

INT 测试过程以“测试计划”为主业务对象，用例、缺陷、评审结果、排期、报告均围绕测试计划展开。

### 1.2 目录结构

测试计划目录结构固定为两级自动目录，下方直接承载测试计划数据：

```text
所属系统
└─ 总需求编号-需求名称
   └─ 测试计划数据
```

要求：

1. “所属系统”目录根据全流程平台传入的系统信息自动创建。
2. “总需求编号-需求名称”目录根据原始需求信息自动创建。
3. 需求编号属于测试计划数据字段，不作为目录层级。
4. 上述两级目录属于系统自动创建目录，但当前不额外强制限制人工修改、移动或重命名。
5. 同一“所属系统 + 总需求编号”下允许存在多条测试计划数据，不按一对一关系限制。

## 2. 全流程平台两次触发

### 2.1 第一次触发：原始需求

全流程平台创建原始需求后，向测试平台传入至少以下信息：

- 总需求编号
- 需求名称
- 需求类型
- 涉及系统
- 业务需求 ZIP 链接（如有）

测试平台收到后：

1. 根据涉及系统创建或定位“所属系统”目录。
2. 在系统目录下创建或定位“总需求编号-需求名称”目录。
3. 此时不创建“待介入”测试计划数据。

### 2.2 第二次触发：系统子需求

某个系统下的具体需求编号确定后，全流程平台再次发送该系统子需求信息。

测试平台收到后：

1. 根据所属系统、总需求编号定位自动目录。
2. 在该目录下创建测试计划数据。
3. 测试计划初始状态为“待介入”。
4. 需求编号作为测试计划业务字段保存。

### 2.3 多系统需求

`【待确认】` 原始业务需求涉及多个系统时，目前考虑“系统负责人确认一个，全流程平台发送一个”，但该规则尚未正式确认。

`【待确认】` 系统优化需求是否完全不经过系统负责人确认。

## 3. 测试计划状态链

当前主状态链为：

```text
待介入 → 测试计划 → 待审批 → 待测试准备 → 测试准备 → 待测试执行 → 测试执行 → 办结
```

### 3.1 状态流转原则

1. 当前状态仅展示合法的下一状态，不允许任意跳转。
2. 自动流转只在明确的系统条件满足时发生。
3. 需要记录实际开始/结束时间的节点由人员主动操作完成。
4. 冒烟测试不作为独立主状态。

### 3.2 待介入 → 测试计划

进入“待介入”后，规格说明书和开发计划预期完成时间可以分开到达。

满足以下两个条件后自动进入“测试计划”：

```text
规格说明书已存在
+
开发计划预期完成时间已存在
```

### 3.3 测试计划 → 待审批

测试团队负责人完成计划编制并提交后，状态进入“待审批”。

### 3.4 待审批

测试总负责人在测试平台完成审批：

- 审批通过：进入“待测试准备”。
- 审批驳回：返回“测试计划”，保留审批意见后重新调整和提交。

## 4. 测试计划编制

### 4.1 准备与执行分别排期

测试准备人员和测试执行人员允许不同，分别维护排期。

测试准备安排至少包括：

- 执行人
- 计划准备开始日期
- 计划准备结束日期

测试执行安排至少包括：

- 执行人
- 计划执行开始日期
- 计划执行结束日期

要求：

1. 同一阶段支持多人。
2. 每个人维护自己的计划开始、结束日期。
3. 同一人员可以同时参与准备与执行，也可以只参与其中一个阶段。
4. 测试计划需要记录是否需要冒烟测试。

## 5. 人员排期与空闲时间

### 5.1 冲突判断

编制或调整测试计划时，系统需要检查执行人在目标日期范围内是否已被其他测试计划占用。

判断规则：

1. 查询该人员在其他“未办结”测试计划中的最新有效排期。
2. 测试准备排期与测试执行排期统一参与冲突判断。
3. 按自然日期区间是否重叠判断冲突。
4. 不考虑法定节假日、调休、补班。
5. 暂不计算半天或小时级冲突。
6. 暂不计算复杂人员负载比例。
7. 存在冲突时必须提示，但允许继续保存测试计划。
8. 冲突提示应能看到相关冲突计划及冲突日期范围。

### 5.2 人员排期统计

系统需要提供独立的人员排期统计能力，用于编制计划前判断人员空闲情况。

用户可指定统计日期范围，系统至少展示：

- 人员
- 已占用日期/天数
- 空闲日期/天数
- 冲突日期/天数
- 已排测试计划数量
- 具体测试计划明细
- 阶段（测试准备/测试执行）
- 计划开始日期
- 计划结束日期

占用时间存在重叠时，需要先合并日期区间，不能简单累加各计划天数。

### 5.3 Excel 导出

人员排期统计需要支持导出 Excel，便于负责人基于人员空闲时间进一步划分任务。

建议导出至少包含：

- 人员
- 统计开始日期
- 统计结束日期
- 已占用天数
- 空闲天数
- 冲突天数
- 已排计划数
- 测试计划
- 需求编号
- 所属系统
- 阶段
- 计划开始日期
- 计划结束日期
- 是否冲突

## 6. 计划调整

需求变化后，不直接覆盖原计划，而是在原计划基础上创建新的调整计划。

```text
原计划 V1（保留）
→ 新增调整计划 V2
→ 修改人员/时间
→ 填写调整原因
→ V2 成为最新有效计划
```

要求：

1. 历史计划版本保留，不覆盖。
2. 最新计划时间和调整原因同步给全流程平台。
3. 新增调整计划本身不立即触发人员通知。
4. 后续准备、执行提醒和人员冲突统计均以最新有效计划为准。

## 7. 测试准备

### 7.1 待测试准备 → 测试准备

到达最新有效计划的准备开始日期时，应提醒相关人员可以开始测试准备。

测试人员主动点击“开始测试准备”后：

1. 状态进入“测试准备”。
2. 记录实际准备开始时间。

### 7.2 完成测试准备

INT 用例在线下编写和评审，不使用 MeterSphere 原“用例评审”模块作为本流程入口。

测试人员点击“完成测试准备”时：

1. 填写评审结果。
2. 填写评审人员。
3. 上传评审后用例文件。
4. 记录实际准备结束时间。
5. 状态进入“待测试执行”。

## 8. 用例上传与版本识别

### 8.1 当前使用方式

测试人员主要在本地 Excel 中维护用例，不要求在平台页面逐条修改。

当前流程：

```text
完成测试准备时上传评审后用例
→ 测试执行期间继续在本地维护
→ 办结前上传最终实际用例
```

最终用例状态只允许：

- 通过
- 跳过

### 8.2 双版本与差异比对

`【待技术评估】` 是否保存评审后用例与最终用例两个快照。

`【待技术评估】` 是否实现 V1/V2 自动差异比对。

如果实现自动差异比对，必须满足以下原则：

1. 不得按 Excel 行号判断同一条用例。
2. 不得按当前排序序号判断同一条用例。
3. Excel 中用例排序变化不能影响身份判断。
4. 需要存在稳定且不随排序变化的用例标识。
5. 稳定标识可以评估复用现有全局用例编号，或新增计划用例 ID。
6. 如果新增计划用例 ID，该 ID 在用例整个生命周期内保持不变。
7. 新增用例可以在最终文件中以空 ID 表示，导入后由系统生成新 ID。

`【待确认】` 当前实际使用的 Excel 是否已有稳定唯一用例编号。

## 9. 待测试执行与测试执行

### 9.1 执行提醒

到达最新有效计划执行开始日期时，按计划时间提醒相关执行人员。

开发实际完成时间晚于计划执行开始日期，不改变原计划提醒规则。

### 9.2 开始测试执行

测试人员在“待测试执行”状态点击“开始测试执行”时，系统校验全流程平台是否已经提供“开发实际完成时间”。

- 未提供：提示“开发实际完成时间未提供，不能流转”，状态保持不变。
- 已提供：进入“测试执行”，记录实际执行开始时间。

开发实际完成时间的到达本身不自动触发状态流转。

### 9.3 冒烟测试

如果计划标记“需要冒烟测试”，进入正式用例执行前先执行冒烟。

冒烟属于测试执行过程中的前置动作，不单独占用主状态。

`【待确认】` 冒烟需要记录的具体字段、结论和关联信息。

## 10. 测试计划与缺陷

### 10.1 关系模型

缺陷以测试计划为主关联对象，具体测试计划用例为可选关联对象。

```text
测试计划
└─ 缺陷（必须属于测试计划）
   └─ 具体测试计划用例（可选）
```

要求：

1. 测试计划页面提供“关联缺陷”视图。
2. 测试计划“关联缺陷”展示当前计划全部缺陷。
3. 全局“缺陷管理”页面继续保留。
4. 测试计划级缺陷页面属于全局缺陷数据在当前计划上下文中的视图，不另建一套独立缺陷。

### 10.2 新增缺陷

从测试计划“关联缺陷”页面新增缺陷时：

1. 必须关联当前测试计划。
2. 不强制关联具体用例。
3. 用户可选择某条测试计划用例作为次级关联。

从某条测试计划用例中新增缺陷时：

1. 自动关联当前测试计划。
2. 自动关联当前测试计划用例。

### 10.3 解除用例关系

如果缺陷已经属于测试计划并关联某条用例，解除“缺陷-用例”关系时，只解除具体用例关系，缺陷仍保留在当前测试计划中。

`【待技术确认】` 需要确认现有后端新增缺陷接口是否支持只关联测试计划、不关联计划用例，以及解除用例关系时是否能够保留测试计划关系。

## 11. 办结

测试计划办结前需要进行后端校验。

### 11.1 用例校验

最终用例只能存在：

- 通过
- 跳过

不能存在：

- 未执行
- 不通过
- 阻塞

### 11.2 缺陷校验

当前测试计划关联的全部缺陷必须处于“已关闭”状态。

只要存在任意非“已关闭”缺陷，禁止办结。

缺陷是否关联具体用例不影响办结校验，办结始终按测试计划维度检查全部缺陷。

### 11.3 办结动作

校验通过后：

1. 在测试平台完成报告分享和办结。
2. 记录实际执行结束时间。
3. 向全流程平台回传办结状态、实际执行结束时间、报告链接及双方约定统计。
4. 全流程平台收到 INT 办结后如何进入后续流程，不属于测试平台设计范围。

## 12. 通知

测试平台需要按所属系统匹配测试组，并向相关人员发送站内通知。

当前需要通知的场景至少包括：

- 测试计划进入需要负责人处理的阶段
- 到达最新计划准备开始日期
- 到达最新计划执行开始日期

测试组按用户组理解，当前每个组通常只有一个成员，但需求模型不限制以后增加成员。

`【待技术确认】` 优先复用项目现有右上角抽屉式站内通知能力，具体底层实现是否 Kafka 需要结合当前代码确认。

`【待确认】` 多成员测试组下，默认负责人、通知范围和责任归属规则。

## 13. 平台间数据同步

### 13.1 全流程平台 → 测试平台

至少包括：

- 原始需求信息
- 涉及系统信息
- 系统子需求信息
- 规格说明书
- 开发计划预期完成时间
- 开发实际完成时间

### 13.2 测试平台 → 全流程平台

至少包括：

- 审批通过后的最新有效测试计划及人员安排
- 计划调整后的最新计划时间和调整原因
- 实际准备开始时间
- 实际准备结束时间
- 实际执行开始时间
- 办结状态
- 实际执行结束时间
- 测试报告链接
- 双方约定的测试统计信息

## 14. 当前待确认项

以下内容当前不作为已定需求：

1. `【待确认】` 多系统业务需求最终确认和发送规则。
2. `【待确认】` 系统优化是否完全无需系统负责人确认。
3. `【待确认】` 哪些系统最终进入 INT 的筛选规则由谁维护。
4. `【待确认】` 未知系统编码进入测试平台后的处理方式。
5. `【待确认】` 多成员测试组的负责人和通知规则。
6. `【待技术确认】` 站内通知具体复用方式及底层实现。
7. `【待技术评估】` 评审后用例与最终用例是否采用双快照。
8. `【待技术评估】` 是否实现 V1/V2 自动差异比对。
9. `【待确认】` Excel 是否已有稳定唯一用例编号。
10. `【待技术确认】` 计划级缺陷和具体用例关联对现有后端数据结构的兼容方式。
11. `【待确认】` 冒烟过程具体记录字段。

## 15. 当前明确不纳入的内容

1. 不设计全流程平台收到 INT 办结后的后续业务流程。
2. 当前不增加需求取消/撤回流程，领导未提出该场景。
3. 不提前设计复杂自动排班引擎。
4. 不处理法定节假日、调休、补班等工作日日历。
5. 当前不把未完成技术评估的双快照和 V1/V2 差异比对写成强制交付能力。

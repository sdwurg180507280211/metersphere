# INT 测试平台整体需求规格

> 本文件为当前 INT 测试平台业务需求基线。
> 当前业务名称统一使用“测试进度”；底层继续复用 MeterSphere 现有 `test_plan/TestPlan/planId` 技术对象。
> 后续业务确认如有变化，应先更新本文件，再调整 design.md 和代码。

---

## 1. 总体目标与业务术语

新版 INT 主流程围绕“测试进度”展开，用户可见界面不再使用“测试计划”作为新版 INT 主流程名称。

用户可见名称统一为：

```text
测试进度
```

正常主状态链：

```text
待介入
→ 测试进度
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

另增加异常终止状态：

```text
已取消
```

总体原则：

1. 测试进度是新版 INT 测试过程的主业务对象。
2. 用例、缺陷、人员排期、个人实际时间、评审、报告都围绕测试进度展开。
3. 正常主状态不允许任意跳转。
4. 测试平台不提供“退回待介入”功能。
5. 如果业务需求本身发生变化，由全研发流程平台重新创建新需求；原需求进入“已取消”。
6. 历史普通测试计划保持原状，不批量转换为新版 INT 测试进度。
7. 页面名称改为“测试进度”，不要求为了改名重构底层 `test_plan` 表、Java 类或内部参数。

## 2. 系统主数据、测试组与负责人

### 2.1 系统主数据同步

全研发流程平台维护全部系统主数据，并将所有系统同步到测试平台。

测试平台展示和维护以下信息：

| 字段 | 维护方 | 说明 |
|---|---|---|
| 系统名称 | 全研发流程平台 | 测试平台同步保存/展示 |
| 系统简称 | 全研发流程平台 | 用于根据需求编号识别所属系统 |
| 是否纳入 INT | 测试平台 | 测试平台维护，并同步回全研发流程平台 |
| 测试组 | 测试平台 | 测试组等同于 MeterSphere 项目 |
| 测试组负责人 | 测试平台 | 乙方负责人，负责接活、派活、编制测试进度 |
| 总负责人 | 测试平台 | 甲方领导，负责审批，不参与具体测试执行 |

系统名称、系统简称由全研发流程平台负责增删改；测试平台只在同步来的系统基础上维护 INT 测试属性。

测试平台修改“是否纳入 INT、测试组、测试组负责人、总负责人”等测试属性后，需要同步回全研发流程平台。

### 2.2 测试组

测试组等同于 MeterSphere 项目。

一个测试组可以对应一个或多个所属系统，也可以配置一个或多个测试组负责人。

### 2.3 测试组负责人与总负责人

测试组负责人：

- 乙方角色。
- 负责测试任务承接、派活、测试进度编制和提交审批。
- 可以作为新建测试进度的默认负责人。
- 默认负责人不是强制负责人，当前测试进度负责人允许后续修改。
- 一个测试组允许配置多个测试组负责人。

总负责人：

- 甲方领导角色。
- 不参与具体测试准备、测试执行和派活。
- 负责测试进度审批。
- 一个总负责人可以对应多个测试组负责人。
- 总负责人和测试组负责人职责不同，业务上不存在角色冲突。

### 2.4 多测试组负责人当前规则

当某个系统/测试组配置多个测试组负责人时，当前暂定：

```text
创建测试进度时默认取配置顺序中的第一个测试组负责人
```

该规则为当前阶段临时规则，后续继续讨论是否增加显式默认负责人、认领机制或其他分配方式。

## 3. 总需求、需求编号与所属系统

### 3.1 核心上游字段

| 业务字段 | 上游字段 | 含义 |
|---|---|---|
| 总需求编号 | `parentWfinstCode` | 一条跨系统的原始需求标识 |
| 需求编号 | `dmpNum` | 原始需求落到具体系统后的系统需求编号 |
| 需求名称 | `name1` | 原始需求名称 |

要求：

1. 一个总需求可以关联多个需求编号。
2. 一个总需求可以涉及多个系统。
3. `dmpNum` 是测试平台识别同一具体需求和后续消息匹配的稳定业务键。
4. 需求规格说明书、开发计划预期完成时间、开发实际完成时间等后续消息按 `dmpNum` 定位原测试进度。
5. 目录只负责展示和组织，不作为后续业务消息匹配依据。

### 3.2 所属系统和负责人确定时机

创建测试进度时已经获得需求编号，因此创建阶段即可确定：

```text
需求编号
→ 所属系统
→ 测试组（项目）
→ 测试组负责人
→ 总负责人
```

因此：

1. 所属系统在测试进度创建阶段已经确定。
2. 测试组、默认测试组负责人和总负责人也在创建阶段确定。
3. 后续人工“移动”只是目录归档动作，不负责判断所属系统，不负责决定负责人。
4. 测试进度业务归属和负责人不依赖谁执行移动操作。

## 4. 公共池、测试进度创建与目录移动

### 4.1 公共池

所有进入新版 INT 流程的需求首先进入公共池。

公共池按总需求组织：

```text
公共池
└─ 总需求编号-需求名称
   ├─ 需求编号 A
   ├─ 需求编号 B
   └─ 需求编号 C
```

总需求目录右侧可以展示原始业务需求 ZIP 链接等上游资料，供测试组负责人查看需求内容。

### 4.2 测试进度只能在公共池首次创建

固定规则：

> 新版 INT 测试进度只能在公共池中首次创建。

要求：

1. 需求同步进入公共池后，由系统在公共池当前需求位置自动创建对应测试进度数据。
2. 测试进度创建成功之前，不允许移动该需求。
3. “移动”操作在测试进度尚未创建时必须隐藏或置灰。
4. 不允许测试组负责人仅根据 ZIP 内容提前把需求移出公共池。
5. 测试进度创建成功后才允许执行目录移动。
6. 移动时迁移已经存在的“需求 + 测试进度及其关联关系”，不得重新创建第二条测试进度。

页面可区分：

```text
进度创建中 → 不允许移动
测试进度已创建 → 允许移动
```

### 4.3 目录移动

同一总需求涉及多个系统时，在总需求目录右侧下拉操作中提供“移动”。

操作流程：

1. 点击总需求目录右侧“移动”。
2. 选择本次需要移动的一个或多个具体需求编号。
3. 选择目标系统目录。
4. 系统校验目标系统是否与需求编号已经确定的所属系统一致。
5. 在目标系统下创建或定位“总需求编号-需求名称”目录。
6. 将选中的具体需求及其已创建测试进度移动到该目录。
7. 未选中的其他需求继续留在公共池或原目录。
8. 目标系统下已存在同一“总需求编号-需求名称”目录时，直接复用，不重复创建。

移动不改变需求编号、所属系统、测试组、默认负责人和总负责人。

## 5. 测试进度创建、幂等与待介入

### 5.1 创建结果

进入 INT 公共池的具体需求按 `dmpNum` 创建唯一测试进度。

创建时至少完成：

1. 保存总需求编号、需求编号、需求名称。
2. 根据需求编号确定所属系统。
3. 根据所属系统确定测试组。
4. 读取测试组负责人和总负责人。
5. 创建底层 `test_plan` 数据。
6. 当前测试进度负责人默认取测试组负责人；多负责人时暂取第一个。
7. 测试进度初始状态为“待介入”。
8. 首次创建位置必须位于公共池对应总需求目录。
9. 创建成功后才开放“移动”。
10. 当前测试进度负责人后续允许有权限人员修改。

### 5.2 幂等

1. 同一 `dmpNum` 重复同步不得重复创建第二个测试进度。
2. 后续规格说明书、开发计划预期完成时间、开发实际完成时间等都更新原测试进度。
3. 同一总需求新增新的 `dmpNum` 时，新建独立测试进度。
4. 不通过测试进度名称或目录名称判断是否重复。

### 5.3 待介入

以下信息可以分开到达：

- 需求规格说明书链接。
- 开发计划预期完成时间。

两项同时存在后：

```text
待介入 → 测试进度
```

只收到其中一项时继续保持“待介入”。

目录是否已经移动到所属系统，不影响业务归属和状态判断。

## 6. 测试进度状态机

### 6.1 正常状态链

```text
待介入
→ 测试进度
→ 待审批
→ 待测试准备
→ 测试准备
→ 待测试执行
→ 测试执行
→ 办结
```

### 6.2 已取消

“已取消”是异常终止状态，不属于正常下一节点。

当全研发流程平台确认原需求取消/废弃后：

1. 原测试进度进入“已取消”。
2. 原需求不允许退回“待介入”。
3. 新业务需求由全研发流程平台重新提出并产生新的需求编号。
4. 新需求重新进入公共池并重新走流程。

进入“已取消”后：

- 停止占用人员正式排期。
- 取消尚未发送的准备/执行提醒。
- 停止每日催办。
- 禁止继续测试准备、测试执行、审批和办结。
- 历史排期、审批、用例、缺陷、报告、实际时间和操作记录全部保留。

### 6.3 主状态流转

1. `待介入 → 测试进度`：规格说明书和开发计划预期完成时间齐全后自动流转。
2. `测试进度 → 待审批`：测试组负责人完成编制并提交。
3. `待审批 → 待测试准备`：总负责人审批通过。
4. `待审批 → 测试进度`：总负责人审批驳回。
5. `待测试准备 → 测试准备`：第一个测试准备人员成功执行“开始准备”后进入。
6. `测试准备 → 待测试执行`：完成整体“完成测试准备”业务动作，评审登记和评审后用例导入成功。
7. `待测试执行 → 测试执行`：第一个测试执行人员成功执行“开始执行”，且开发实际完成时间已存在。
8. `测试执行 → 办结`：办结校验全部通过后人工办结。
9. 冒烟测试不单独增加主状态。
10. 不提供任意状态手工跳转和“退回待介入”。

## 7. 测试进度页面与人员安排

### 7.1 页面定义

“测试进度页面”就是现有 MeterSphere “测试计划页面”改名后的页面，不新增“测试进度详情页”或另一套页面。

用户可见菜单、页面标题、列表名称、字段名称和业务文案统一使用“测试进度”。

### 7.2 人员安排入口

测试进度页面提供：

```text
【人员安排】
```

点击后打开人员安排弹窗。

人员安排弹窗包含两个页签：

```text
测试准备
测试执行
```

### 7.3 测试准备人员字段

每一名测试准备人员分别维护 4 个时间字段：

- 计划准备开始时间。
- 计划准备结束时间。
- 实际准备开始时间。
- 实际准备结束时间。

推荐列表：

| 人员 | 计划开始 | 计划结束 | 实际开始 | 实际结束 | 操作 |
|---|---|---|---|---|---|
| 张三 | 9/20 | 9/22 | -- | -- | 开始准备 |
| 李四 | 9/21 | 9/23 | 9/21 09:10 | -- | 结束准备 |
| 王五 | 9/20 | 9/22 | 9/20 09:05 | 9/22 16:30 | 已完成 |

### 7.4 测试执行人员字段

每一名测试执行人员同样分别维护 4 个时间字段：

- 计划执行开始时间。
- 计划执行结束时间。
- 实际执行开始时间。
- 实际执行结束时间。

如果同一人员同时参与测试准备和测试执行，则该人员最多存在 8 个阶段时间字段；准备和执行两套时间相互独立。

### 7.5 实际时间来源

个人实际开始/结束时间不得由负责人在排期表中直接手工填写。

实际时间由测试人员执行个人动作时记录当前系统时间：

测试准备：

```text
开始准备
结束准备
```

测试执行：

```text
开始执行
结束执行
```

按钮状态规则：

- 实际开始为空：显示“开始准备/开始执行”。
- 实际开始有值、实际结束为空：显示“结束准备/结束执行”。
- 实际开始和实际结束均有值：显示“已完成”。

个人按钮用于记录个人真实工作时间，不等同于整个测试进度阶段完成。

## 8. 测试进度编制、排期和空闲统计

### 8.1 编制字段

测试进度编制至少展示：

- 总需求编号。
- 需求编号。
- 需求名称。
- 所属系统。
- 测试组。
- 测试组负责人。
- 总负责人。
- 当前测试进度负责人。
- 需求规格说明书。
- 开发计划预期完成时间。
- 开发实际完成时间。
- 是否需要冒烟测试。

当前测试进度负责人创建时默认取测试组负责人，但允许有权限人员修改。

### 8.2 人员排期

测试准备和测试执行分别排期。

要求：

1. 同一阶段支持多人。
2. 每个人独立维护计划开始和计划结束时间。
3. 准备人员和执行人员可以不同。
4. 同一人员可以同时参与准备和执行。
5. 保存/提交时检查与其他未办结测试进度的人员计划排期冲突。
6. 冲突需要提示，但当前允许继续保存/提交。
7. 不处理半天、小时级排期和复杂负载百分比。

### 8.3 空闲与占用统计

人员排期统计至少支持：

- 人员。
- 已占用日期/天数。
- 空闲日期/天数。
- 冲突日期/天数。
- 已排测试进度数量。
- 测试进度。
- 所属系统。
- 需求编号。
- 阶段。
- 计划开始和结束时间。
- 实际开始和结束时间。

当前口径：

1. 未来排期、空闲和冲突判断以最新有效的计划开始/结束时间为主要依据。
2. 实际开始/结束时间用于统计真实投入、延期、提前完成等实际执行情况。
3. “提前实际结束后是否立即自动释放剩余计划占用”暂不自动写死，作为后续待确认规则。
4. “已取消”测试进度不再占用当前有效排期，但历史排期和实际记录仍保留。
5. 支持 Excel 导出。

## 9. 测试进度审批与调整版本

### 9.1 V1 审批

测试组负责人完成首次编制后提交：

```text
测试进度 → 待审批
```

由对应总负责人审批。

审批结果：

- 通过：`待审批 → 待测试准备`
- 驳回：`待审批 → 测试进度`

审批通过和驳回均保存操作人、时间和审批意见，历史不得覆盖。

### 9.2 排期/人员调整

业务需求本身发生变化时，不在原测试进度内做排期版本调整，而是由全研发流程平台重新提需求，原需求进入“已取消”。

如果需求本身不变，仅测试人员和日期发生调整，可以在同一测试进度下形成 V1/V2/V3 等调整版本。

规则：

1. 原有效版本保留，不覆盖、不删除。
2. 调整版本审批通过前，当前有效版本继续生效。
3. 调整版本审批通过后，新版本成为最新有效版本。
4. 调整版本驳回后，原有效版本继续生效。
5. 后续计划提醒、排期占用和对外同步以最新有效版本为准。
6. 日期调整后取消旧日期尚未发送的提醒，并按新有效日期重新计算提醒。
7. 已产生的个人实际开始/结束时间不得因单纯计划版本调整被静默覆盖；具体调整后的关联方式由 design.md 明确。

## 10. 个人测试准备动作与整体测试准备状态

### 10.1 提前开始和提前结束

测试人员允许在计划时间之前主动操作。

例如计划准备时间为 9/20～9/22：

- 9/19 点击“开始准备”，实际准备开始时间记录为 9/19 的真实点击时间。
- 9/21 点击“结束准备”，实际准备结束时间记录为 9/21 的真实点击时间。

提前操作后，对应的计划到期提醒不再发送。

### 10.2 第一个人开始准备

当整体状态为“待测试准备”时：

1. 第一个测试准备人员点击“开始准备”。
2. 系统记录该人员的实际准备开始时间。
3. 同时将整体测试进度从“待测试准备”流转为“测试准备”。

其他测试准备人员后续点击“开始准备”时，只记录各自实际准备开始时间，不重复改变整体状态。

### 10.3 个人结束准备

测试人员点击“结束准备”后，只记录本人实际准备结束时间。

即使所有测试准备人员都已经结束，也不自动进入“待测试执行”。

### 10.4 整体完成测试准备

“结束准备”和“完成测试准备”是两个不同业务动作：

```text
个人【结束准备】
→ 记录本人实际准备结束时间

整体【完成测试准备】
→ 完成评审登记、评审后 Excel 校验与结构化导入
→ 测试准备 → 待测试执行
```

整体“完成测试准备”仍由测试组负责人或具备授权的人员执行。

## 11. 评审、Excel 标签与用例基线

### 11.1 测试准备评审

点击整体“完成测试准备”时，至少登记：

- 评审结果：通过/不通过。
- 评审人员。
- 评审意见。
- 评审后用例 Excel。

规则：

1. 评审通过时，评审人员必填、Excel 必填，评审意见可选。
2. 评审不通过时，评审人员必填、评审意见必填，Excel 可不上传。
3. 评审不通过继续保持“测试准备”，后续可重新评审；每轮完整留痕。
4. 评审通过后必须先完成 Excel 校验和结构化导入；导入失败不能进入“待测试执行”。
5. 第一次评审通过且导入成功的数据保存为首次评审后用例基线。

### 11.2 标签为用例稳定标识

新版 INT Excel 用例以“标签”作为同一测试进度内的稳定用例标识，例如：

```text
标签    用例名称
L001    正常登录
L002    密码错误
L003    用户锁定
```

固定规则：

1. Excel 必须包含“标签”列。
2. 每条用例标签必须有值。
3. 标签在同一个测试进度内唯一。
4. 不同测试进度之间允许重复使用 `L001/L002` 等标签。
5. 同一测试进度内重复标签时整批导入失败。
6. 缺少标签列或存在空标签时整批导入失败。
7. Excel 行号和页面排序不能作为用例身份。
8. 平台不为缺失标签的用例自动生成标签后继续导入。

### 11.3 最终用例和差异

办结前上传最终 Excel，并与首次评审后固定基线进行比较：

| 差异类型 | 识别规则 |
|---|---|
| 新增 | 最终 Excel 存在、基线不存在的标签 |
| 删除 | 基线存在、最终 Excel 不存在的标签 |
| 修改 | 标签相同，但纳入比较的用例定义字段发生变化 |

单纯调整 Excel 行顺序不算修改。

如果已有用例标签被改成新标签，当前按“原标签删除 + 新标签新增”处理。

## 12. 个人测试执行动作与整体测试执行状态

### 12.1 测试执行同样按人员记录 4 个时间

每名执行人员独立维护：

- 计划执行开始时间。
- 计划执行结束时间。
- 实际执行开始时间。
- 实际执行结束时间。

### 12.2 开始执行

测试人员点击“开始执行”时，系统必须先校验全研发流程平台是否已经提供开发实际完成时间。

未提供时：

```text
开发实际完成时间未提供，不能开始测试执行
```

不写入个人实际执行开始时间，也不改变整体状态。

已提供时：

1. 记录当前人员实际执行开始时间。
2. 如果该人员是第一个成功开始执行的人，则整体状态从“待测试执行”进入“测试执行”。
3. 其他执行人员后续开始只记录自己的实际执行开始时间。

开发实际完成时间到达本身不自动推进主状态。

### 12.3 结束执行

测试人员点击“结束执行”后，只记录本人实际执行结束时间。

即使所有执行人员均已结束，也不自动办结。

整体办结仍需完成最终 Excel、用例状态、缺陷、冒烟和报告等校验后，由具备权限的人员执行“办结”。

## 13. 冒烟测试

是否需要冒烟在测试进度编制阶段确定。

冒烟属于测试执行阶段内部的前置过程，不新增主状态。

至少记录：

- 通过/不通过。
- 实际执行人。
- 执行时间。
- 备注。
- 关联缺陷（如有）。

需要冒烟时，最近一次冒烟未通过前禁止正式执行用例；冒烟失败后允许再次冒烟，每轮结果保留历史。

## 14. 缺陷与办结

### 14.1 缺陷

缺陷继续复用 MeterSphere 现有缺陷数据。

关系：

```text
测试进度
└─ 缺陷（必须属于测试进度）
   └─ 具体用例（可选）
```

要求：

1. 测试进度页面增加“关联缺陷”视图。
2. 从测试进度新增缺陷时必须关联当前测试进度，不强制关联具体用例。
3. 从具体用例新增缺陷时同时关联测试进度和该用例。
4. 解除用例关联时只解除具体用例关系，缺陷仍保留在测试进度中。
5. 已取消测试进度的历史缺陷保留可追溯。

### 14.2 办结

办结前至少满足：

1. 当前主状态为“测试执行”。
2. 需要冒烟时最近一次冒烟为通过。
3. 最终 Excel 已成功校验并结构化导入。
4. 已完成最终 Excel 与首次评审后基线的新增/删除/修改比对。
5. 最终测试用例只存在“通过/跳过”。
6. 当前测试进度全部缺陷达到允许办结状态。
7. 报告生成/保存成功。

缺陷允许办结状态当前为：

```text
已关闭
或
已取消
```

所有个人执行人员均结束，不等同于整体“办结”。

## 15. 站内通知、个人快捷按钮与持续催办

### 15.1 通知是快捷操作入口，不是自动流转

通知本身、打开通知、阅读通知都不能改变个人实际时间或测试进度状态。

通知中可以直接提供与“人员安排”弹窗相同的个人动作按钮，用户不需要先跳转到测试进度页面再点第二次。

通知按钮与人员安排弹窗按钮必须调用同一套业务校验和后端动作。

### 15.2 测试准备开始提醒

针对每一名测试准备人员单独判断。

当满足：

```text
当前日期达到该人员计划准备开始日期
且
该人员实际准备开始时间为空
```

则计划开始日 09:00 首次提醒：

```text
你的测试准备计划已到开始时间，请及时开始测试准备

【开始准备】 【查看测试进度】
```

如仍未开始，此后每天 09:00 继续提醒，直到实际准备开始时间产生。

如果人员提前点击“开始准备”，则不再发送开始提醒。

### 15.3 测试准备结束提醒

针对每一名测试准备人员单独判断。

当满足：

```text
当前日期达到该人员计划准备结束日期
且
该人员实际准备开始时间已有值
且
该人员实际准备结束时间为空
```

则计划结束日 09:00 首次提醒：

```text
你的测试准备计划已到结束时间，请及时结束测试准备

【结束准备】 【查看测试进度】
```

如仍未结束，此后每天 09:00 继续提醒，直到实际准备结束时间产生。

如果计划结束日到达时该人员仍未开始，则继续发送“开始准备”提醒，不同时发送相互矛盾的“结束准备”提醒。

### 15.4 测试执行开始提醒

针对每一名测试执行人员单独判断。

当达到该人员计划执行开始日期且实际执行开始时间为空时，计划开始日 09:00 提醒：

```text
你的测试执行计划已到开始时间，请及时开始测试执行

【开始执行】 【查看测试进度】
```

此后每天 09:00 催办，直到实际执行开始时间产生。

点击通知中的“开始执行”仍必须校验开发实际完成时间，不能绕过业务门禁。

### 15.5 测试执行结束提醒

当达到该人员计划执行结束日期，且实际执行开始已有值、实际执行结束为空时，计划结束日 09:00 提醒：

```text
你的测试执行计划已到结束时间，请及时结束测试执行

【结束执行】 【查看测试进度】
```

此后每天 09:00 催办，直到实际执行结束时间产生。

### 15.6 通知变更

1. 排期日期调整后，取消旧有效日期对应的尚未发送提醒和后续催办，按最新有效日期重新计算。
2. 测试进度进入“已取消”后，取消所有未发送提醒并停止每日催办。
3. 对应个人实际开始/结束时间已经产生后，不再发送该个人对应动作的催办。
4. 当前提醒时间统一为每天 09:00，不额外区分法定节假日、调休和补班。
5. 通知中的历史按钮再次点击时，必须重新校验当前状态、当前人员记录和操作权限；已完成、已取消、已失效时不得重复写入时间。

## 16. 页面操作层级

需要明确区分“个人动作”和“整体阶段动作”。

### 16.1 个人动作

位于：

```text
测试进度页面（原测试计划页面）
→ 人员安排
→ 测试准备 / 测试执行
→ 当前人员所在行
```

包括：

- 开始准备。
- 结束准备。
- 开始执行。
- 结束执行。

作用：只记录该人员自己的实际时间；其中第一个成功开始准备/执行的人可以触发对应整体阶段开始。

### 16.2 整体阶段动作

包括：

- 提交测试进度。
- 审批通过/驳回。
- 完成测试准备。
- 冒烟测试。
- 办结。

整体阶段动作不用于代替个人实际开始/结束时间记录。

特别说明：

```text
个人【结束准备】 ≠ 整体【完成测试准备】
个人【结束执行】 ≠ 整体【办结】
```

## 17. 平台间数据同步

### 17.1 全研发流程平台 → 测试平台

| 需求取消/废弃 | `dmpNum` + 取消/废弃信息 |

### 17.2 测试平台 → 全研发流程平台

至少包括：

| 事件 | 主要数据 |
|---|---|

| 办结 | 办结状态、报告链接和必要统计 |

系统名称和简称仍以全研发流程平台主数据为来源；测试属性由测试平台维护并回传。

## 18. 待确认事项

以下内容仍需后续继续讨论：

1. 一个系统/测试组配置多个测试组负责人时，目前创建测试进度默认取第一个；后续是否增加显式默认负责人、认领机制或其他分配方式。
2. 测试组负责人的最终配置入口是否完全落在项目成员管理，还是由独立“项目-所属系统-负责人”配置统一维护。
3. 总负责人是否允许同一系统配置多人，以及多人审批是任一人通过、指定人审批还是会签。
4. 人员提前实际结束后，是否立即自动释放剩余计划占用，还是仍以有效计划结束日期为正式排期占用终点。
5. 是否允许测试组负责人或管理员代测试人员点击个人“开始/结束”按钮；当前业务原则按本人记录真实时间理解，代操作规则尚未正式确认。

## 20. 本次明确不做的事情

1. 不允许测试平台人工把未办结测试进度退回“待介入”。
2. 不因业务需求变化直接覆盖原需求；业务变化由全研发重新提新需求，原需求进入“已取消”。
3. 不因取消而物理删除历史排期、审批、用例、缺陷、实际时间和操作记录。
4. 不允许测试进度创建成功前把需求从公共池移出。
5. 不通过目录路径识别同一需求或匹配后续消息。
6. 不为 INT 重新建设独立缺陷系统。
7. 不使用 Excel 行号、页面排序代替用例“标签”识别用例。
8. 不为缺失标签的用例自动生成标签后继续导入。
9. 不建设复杂自动排班引擎、小时/半天级冲突和复杂负载百分比。
10. 不为了业务名称“测试进度”而重命名底层 `test_plan` 技术对象。
11. 不因为个人测试准备全部结束而自动进入“待测试执行”。
12. 不因为个人测试执行全部结束而自动“办结”。
13. 不因为到达计划开始/结束日期而自动写入个人实际时间。
14. 不因为打开通知或打开测试进度页面而自动改变状态或实际时间。
15. 不批量把历史普通测试计划转换为新版 INT 测试进度。

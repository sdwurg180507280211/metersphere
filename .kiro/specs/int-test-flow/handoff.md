## 二、已定口径（2026-10-23 逐条确认）

1. **术语**：测试计划、测试进度、需求、计划指的是同一个东西（`test_plan`）。页面「测试计划」改名为「测试进度」。隐藏「功能用例」和「用例评审」两个菜单。
2. **节奏**：先在本地开发并自测跑通（阶段一用模拟 MQ 消息），然后再和研发平台对接（阶段二）。
3. **状态链**：待介入 → 测试计划 → 待审批 → 待测试准备 → 测试准备 → 待测试执行 → 测试执行 → 办结。
4. **需求池**：每个项目左侧模块树的第一级只有一个「需求池」目录。
   - 原始需求进来时会带上涉及的系统，据此在需求池下建目录「总需求编号-需求名称」。
   - 系统需求确认后，在该目录下自动建一条计划，状态为「待介入」。之后等人工拖动归位，拖动不作为流转条件。
   - 匹配不到系统的需求不接收。
   - dmpNum（系统子需求编号）全局唯一。
5. **自动流转**：「规格说明书链接」和「开发计划完成时间」两项都到齐后，自动从待介入进入「测试计划」，并通知测试组。只看这 2 个条件，原先的第三条「移出公共池」已取消。
6. **研发平台传入的字段**：
   - 原始需求：总需求编号、需求名称、需求类型、业务需求 ZIP 链接。
   - 系统子需求：需求编号。
   - 另有：规格说明书链接、开发计划完成时间、开发实际完成时间。
7. **回传只有两次**：
   - 首次审批通过时：需求编号、最早的「测试准备计划开始时间」、最晚的「测试执行计划结束时间」。
   - 办结时：需求编号和办结标志。
   - 其它任何时候都不回传。
8. **需求变更**：研发平台不能修改需求，只能新提一条，原需求作废。
   - 新需求对应的计划显示为「V2」。组负责人在编制新计划时选择「替代哪条原计划」。
   - 被替代的原计划：停止提醒、释放排期、变为只读的「已废弃」。
   - 没有废弃按钮，测试人员通过口头通知。
9. **已审批计划的修改**：可以改人员或日期，必须填原因，然后重新审批，版本号不变。
   - 新安排审批通过前，旧安排继续有效。
   - 已经开始工作的人不能移除。
   - 修改不触发回传。
10. **人员时间**：每人有自己的计划和实际时间，分准备、执行两段。开始、结束只能本人点。每天 09:00（Asia/Shanghai）催办。
11. **通知**：只发站内通知。
12. **评审**：评审在线下进行。线上只做两件事：导入评审后的 Excel，再点「通过」。
13. **用例**：Excel 的「标签」列作为唯一 ID，去掉首尾空格、不区分大小写、同一计划内唯一。
    - 基线版和最终版之间做差异比对，比对字段：名称、前置、步骤、预期、等级。执行结果单独展示。
14. **冒烟**：就是新建一条「阻断」级缺陷，不另做冒烟轮次。
15. **缺陷**：在计划行的操作列加「新建缺陷」和「关联缺陷」两个按钮，自动填好「缺陷来源」和「需求号」，用的是已有字段。
16. **办结**：条件是关联用例只有「通过」或「跳过」，关联缺陷都是「已关闭」或「已取消」。
17. **报告**：沿用现有报告，加一节 INT 内容。

## 六、操作注意

- Mac 的 sshd 会对频繁连接做节流，症状是 `kex_exchange_identification: Connection closed`，等 10 分钟左右会恢复。命令要尽量合并到一次连接里执行。
- Mac 上的命令要先 `export LANG=en_US.UTF-8`。路径是 NFD 编码，进目录要用 glob 或 find，不要直接手打中文路径。zsh 下 `--include="*.java"` 要加引号，也不要用 `==`。
- Mac 上有 openpyxl 和 python-pptx，没有 python-docx，docx 要用 zipfile 直接读 XML。
